# Linux & Shell

Content is current to 2026 (systemd-based distros, `ss` over `netstat`, Bash 5.x).

## 🟢 Basic (0–2 yrs)

### Q1. [Theory] Describe the Linux filesystem hierarchy. What lives in /etc, /var, /usr, /tmp, /proc, and /opt?

Linux uses a single rooted tree (`/`) defined by the Filesystem Hierarchy Standard (FHS); there are no drive letters like `C:`. Every device, partition, or network share is *mounted* somewhere under `/`.

```
/            root of everything
├── bin      essential user binaries (often a symlink to /usr/bin now)
├── boot      kernel, initramfs, bootloader files
├── dev       device files (/dev/sda, /dev/null, /dev/random)
├── etc       system-wide configuration (text files), no binaries
├── home      per-user home directories (/home/alice)
├── lib       shared libraries for /bin and /sbin
├── opt       optional / third-party software (often vendor apps)
├── proc      virtual FS exposing kernel & process state (/proc/<pid>)
├── root      home directory of the root user
├── sys       virtual FS exposing devices & kernel objects (sysfs)
├── tmp       temporary files, world-writable, cleared on reboot
├── usr       user programs & read-only data (/usr/bin, /usr/lib)
└── var       variable data: logs (/var/log), spools, caches, /var/lib
```

Key ones interviewers probe: `/etc` is configuration (and only config — it should never hold large binaries); `/var/log` is where almost all logs land; `/proc` and `/sys` are *virtual* — they are generated by the kernel in memory, not stored on disk, and reading `/proc/cpuinfo` or `/proc/<pid>/status` is how many tools get their data. `/tmp` is world-writable but cleaned on reboot; `/opt` is the conventional home for self-contained third-party packages.

### Q2. [Practical] How do you read and interpret the permission string `-rwxr-xr--` from `ls -l`?

`ls -l` prints a 10-character mode string. The first character is the file *type*; the next nine are three permission triads for **owner**, **group**, and **other**.

```
- rwx r-x r--
│ │   │   └── other:  r--   read only
│ │   └────── group:  r-x   read + execute
│ └────────── owner:  rwx   read + write + execute
└──────────── type:   -     regular file (d=dir, l=symlink, c/b=device)
```

Each triad maps to octal: `r=4, w=2, x=1`. So `rwxr-xr--` = `4+2+1 / 4+0+1 / 4+0+0` = **754**. On a *directory*, `x` means "can enter/traverse" (cd into it) and `r` means "can list its contents" — a subtle but frequently tested distinction.

```bash
ls -l file.sh        # -rwxr-xr-- 1 alice devs 220 Jun 30 file.sh
stat -c '%A %a %U:%G' file.sh   # symbolic + octal + owner:group
```

### Q3. [Practical] How do you change file permissions and ownership? Give symbolic and octal `chmod`, plus `chown`.

```bash
# Octal (absolute) — set exactly these bits
chmod 644 file.txt        # rw-r--r--
chmod 755 script.sh       # rwxr-xr-x  (typical for executables/dirs)
chmod 600 ~/.ssh/id_rsa   # rw-------  (private key must be owner-only)

# Symbolic (relative) — add/remove specific bits
chmod u+x deploy.sh       # add execute for owner
chmod go-w shared.conf    # remove write from group + other
chmod a+r report.txt      # add read for all (a = ugo)

# Recursively on a tree (careful!)
chmod -R 750 /opt/app

# Ownership: chown user:group
chown alice:devs app.jar          # change both
chown :devs app.jar               # change only group
chown -R deploy:deploy /var/www   # recursive
```

A common gotcha: never blanket `chmod -R 777` to "fix" a permission problem — it makes files world-writable and is a real security finding. Prefer the least-privilege bits that actually solve the issue.

### Q4. [Theory] What is `umask` and how does it affect newly created files?

`umask` is a *mask* of permission bits that are **removed** from the default mode of newly created files and directories. The base default is `666` (rw for all) for files and `777` for directories; the umask is subtracted (bitwise AND with the complement).

```
default file mode 666  -  umask 022  =  644 (rw-r--r--)
default dir  mode 777  -  umask 022  =  755 (rwxr-xr-x)
```

A typical interactive umask is `022` (group/other lose write). For tighter setups, `027` removes all bits from "other" so new files aren't world-readable. You set it in `/etc/profile` or a shell rc file:

```bash
umask          # print current mask, e.g. 0022
umask 027      # group: no write; other: nothing
```

Note umask only *removes* bits; it can never grant execute on a file that the creating program didn't request — that's why a freshly `touch`ed file is never executable regardless of umask.

### Q5. [Practical] What are the most important navigation and inspection commands a new engineer must know?

```bash
pwd                 # print working directory
cd /var/log         # change directory (cd - = previous, cd = home)
ls -lah             # long, all (incl. dotfiles), human-readable sizes
cat file            # dump whole file
less file           # paged viewer (q to quit, / to search) — safe for huge files
head -n 20 file     # first 20 lines
tail -n 50 file     # last 50 lines
tail -f app.log     # follow appended lines live (essential for logs)
file mystery.bin    # identify file type by content
which java          # path of the executable that would run
stat file           # size, perms, inode, timestamps
```

Prefer `less` over `cat` for unknown/large files — `cat` on a multi-GB log floods your terminal, while `less` pages lazily. `tail -f` (or `tail -F` which survives log rotation) is the bread-and-butter of watching a running service.

### Q6. [Practical] How do you find files by name and by content?

Two different tools for two different jobs. `find` walks the directory tree by metadata (name, size, time, type); `grep` searches *inside* files.

```bash
# By name (case-insensitive), under /etc
find /etc -iname '*.conf'

# Files larger than 100 MB under /var
find /var -type f -size +100M

# Files modified in the last 24 hours
find . -type f -mtime -1

# By content: recursive, case-insensitive, show line numbers
grep -rin 'connection refused' /var/log

# Just the filenames that match
grep -rl 'TODO' src/
```

`find` is metadata-first; reach for `grep -r` (or `ripgrep`/`rg`, common in 2026) when you need to search *file contents*.

### Q7. [Theory] Explain stdin, stdout, and stderr and their file descriptor numbers.

Every process starts with three open streams, each a numbered file descriptor:

| FD | Name   | Default        | Purpose                          |
|----|--------|----------------|----------------------------------|
| 0  | stdin  | keyboard       | input to the program             |
| 1  | stdout | terminal       | normal output                    |
| 2  | stderr | terminal       | errors / diagnostics             |

Keeping stdout and stderr separate is what lets you pipe *results* onward while still seeing *errors*, or redirect them to different files:

```bash
./app                 # both 1 and 2 go to terminal
./app > out.log       # stdout → file, stderr still on screen
./app 2> err.log      # stderr → file, stdout still on screen
./app > out.log 2>&1  # both → out.log (2>&1 means "fd 2 goes where fd 1 goes")
./app &> all.log      # Bash shortcut for both → file
./app 2>/dev/null     # discard errors
```

A classic bug: writing `./app 2>&1 > out.log` redirects stderr to the *terminal* (where stdout pointed at that moment) and only stdout to the file — order matters, because `2>&1` copies the current target of fd 1.

### Q8. [Practical] What does a pipe (`|`) do, and how is it different from redirection (`>`)?

A pipe connects the **stdout of one process to the stdin of the next**, streaming data between live processes in memory. Redirection (`>`, `<`) connects a stream to a **file**.

```bash
# Pipe: chain three programs, no temp file
ps aux | grep java | wc -l        # count java processes

# Redirection: stream ↔ file
sort names.txt > sorted.txt       # stdout → file (overwrite)
sort names.txt >> sorted.txt      # append
wc -l < sorted.txt                # file → stdin
```

```
ps aux ──stdout──▶| grep java ──stdout──▶| wc -l ──▶ terminal
```

Pipes enable the Unix philosophy: small single-purpose tools composed into pipelines. Use `>` only when you want the result persisted to a file; use `|` to keep data flowing between programs.

### Q9. [Practical] How do you inspect running processes? Compare `ps`, `top`, and `htop`.

```bash
ps aux                 # snapshot of ALL processes (BSD syntax)
ps -ef                 # snapshot (System V syntax) — full command lines
ps aux --sort=-%cpu | head   # top CPU consumers, one-shot
top                    # live, auto-refreshing dashboard
htop                   # nicer interactive top (colors, scroll, tree, F-key kill)
```

- **`ps`** is a one-time *snapshot* — great for scripting and grepping.
- **`top`** is a live, refreshing view of CPU%, MEM%, load average, and per-process stats; press `P` to sort by CPU, `M` by memory, `1` to show per-core CPUs.
- **`htop`** (usually installed separately) is an interactive, colorized `top` with scrolling, a process tree (`F5`), and click-to-kill — the on-call favorite.

Read the columns: in `ps aux`, `%CPU`/`%MEM` are usage, `VSZ` is virtual size, `RSS` is resident (physical) memory in KB, and `STAT` shows state (`R` running, `S` sleeping, `D` uninterruptible I/O, `Z` zombie).

### Q10. [Practical] How do you terminate a process, and what's the difference between `kill`, `kill -9`, and `pkill`?

`kill` sends a *signal* (default `SIGTERM`, 15) to a PID. Most processes catch `SIGTERM` and shut down cleanly (flush buffers, close connections). `SIGKILL` (9) cannot be caught — the kernel destroys the process immediately, risking corrupted state.

```bash
kill 12345           # polite SIGTERM — ask it to stop (preferred)
kill -15 12345       # explicit SIGTERM
kill -9 12345        # SIGKILL — forceful, last resort
pkill -f myapp.jar   # kill by matching the full command line
killall nginx        # kill all processes named exactly "nginx"
```

Best practice: **always try `SIGTERM` first**, give the process a few seconds to exit gracefully, and only escalate to `-9` if it's stuck. A Java app that gets `-9` skips its shutdown hooks — no graceful connection drain, no final log flush.

### Q11. [Theory] What are environment variables, and how do you set them for a session vs. a command?

Environment variables are key-value pairs inherited by child processes — the standard way to pass configuration (paths, credentials, feature flags) into programs without hard-coding.

```bash
echo $PATH                 # read a variable
printenv | sort            # list all env vars
env                        # same

NAME=value                 # shell variable — NOT exported to children
export NAME=value          # environment variable — inherited by children

# Set just for ONE command (scoped, doesn't persist)
DEBUG=true ./run.sh

# Persist for future shells: add `export` lines to ~/.bashrc or ~/.profile
```

The distinction tested most: a bare `NAME=value` is a *shell* variable visible only in the current shell; `export` promotes it to the *environment* so child processes (like your Java app) can read it via `System.getenv("NAME")`. `PATH` is the colon-separated list of directories the shell searches for commands.

### Q12. [Practical] How do you write and run a basic Bash script with a shebang? What does `chmod +x` have to do with it?

```bash
#!/usr/bin/env bash
# hello.sh — greet a user passed as the first argument
set -euo pipefail            # fail fast (see later question)

name="${1:-world}"           # default to "world" if no arg
echo "Hello, ${name}!"
```

```bash
chmod +x hello.sh   # make it executable
./hello.sh Alice    # → Hello, Alice!
bash hello.sh Alice # alternative: run via interpreter, no +x needed
```

The first line is the **shebang** (`#!`): it tells the kernel which interpreter to run the file with. `#!/usr/bin/env bash` finds `bash` on the `PATH` (more portable than hard-coding `/bin/bash`). Without execute permission you must invoke it as `bash hello.sh`; with `chmod +x` you can run it directly as `./hello.sh`.

### Q13. [Coding] Write a Bash script that loops over the lines of a file and prints non-empty, non-comment lines.

```bash
#!/usr/bin/env bash
set -euo pipefail

file="${1:?usage: $0 <file>}"      # error & exit if $1 unset

while IFS= read -r line || [[ -n "$line" ]]; do
    # skip blank lines and lines starting with #
    [[ -z "${line// }" ]] && continue
    [[ "$line" == \#* ]] && continue
    echo "$line"
done < "$file"
```

Key details interviewers look for: `IFS=` prevents leading/trailing whitespace stripping, `read -r` stops backslash mangling, the `|| [[ -n "$line" ]]` clause handles a final line with no trailing newline, and `< "$file"` feeds the file into the loop's stdin (don't use `cat file | while`, which spawns a subshell and loses variable changes).

### Q14. [Theory] What is the exit code (exit status) of a command, and how do you check it?

Every command returns an integer exit status: **`0` means success**, any non-zero (1–255) means failure, with specific codes carrying meaning (e.g. `127` = command not found, `126` = not executable, `130` = terminated by Ctrl-C/SIGINT). The special variable `$?` holds the status of the last command.

```bash
grep -q "ERROR" app.log
echo $?            # 0 if found, 1 if not

if grep -q "ERROR" app.log; then
    echo "errors present"
fi

# Chaining on success/failure
make && ./run        # run only if make succeeded (exit 0)
backup || alert      # alert only if backup failed (non-zero)

exit 1               # make YOUR script signal failure to callers
```

Exit codes are how scripts, CI pipelines, and `systemd` decide whether a step passed. Always `exit` with a meaningful code so callers can react.

### Q15. [Practical] How do you compress and extract archives with `tar` and `gzip`?

`tar` bundles many files into one archive; `gzip`/`bzip2`/`xz` compress it. The flags are the classic mnemonic confusion point.

```bash
# Create a gzipped tarball  (c=create, z=gzip, v=verbose, f=file)
tar -czvf backup.tar.gz /var/www

# Extract  (x=extract)
tar -xzvf backup.tar.gz

# Extract into a specific directory
tar -xzvf backup.tar.gz -C /restore/here

# List contents WITHOUT extracting  (t=list)
tar -tzvf backup.tar.gz

# Plain gzip / gunzip a single file
gzip access.log          # → access.log.gz (original removed)
gunzip access.log.gz     # → access.log
```

Memory hook: **"Create Ze Vile File"** = `czvf`, swap `c`→`x` to extract. Use `-j` for `.tar.bz2` and `-J` for `.tar.xz` (xz gives the best ratio, useful for shipping large artifacts).

### Q16. [Practical] How do you check disk usage with `df` and `du`?

```bash
df -h               # free/used space PER FILESYSTEM, human-readable
df -hT              # also show filesystem type (ext4, xfs, tmpfs)
df -i               # inode usage (can fill up even with free space!)

du -sh /var/log     # total Size of a directory (Human, summary)
du -h --max-depth=1 /var | sort -rh | head   # biggest subdirs of /var
```

- **`df`** answers "how full is the disk/partition?" — it reports per-mount totals.
- **`du`** answers "what's *using* the space *inside* a directory?" — it sums file sizes.

A subtle on-call trap: `df` can report a full disk while `du` finds little — usually a deleted-but-still-open file held by a running process (recover space by restarting it or use `lsof | grep deleted`). Also watch `df -i`: running out of inodes (millions of tiny files) makes a disk "full" with bytes to spare.

### Q17. [Practical] How do you download files or call HTTP APIs from the terminal with `curl` and `wget`?

```bash
# curl: Swiss-army HTTP client (prints to stdout by default)
curl https://api.example.com/health        # GET, body to stdout
curl -s -o data.json https://.../data       # silent, save to file
curl -i https://example.com                  # include response headers
curl -L https://bit.ly/x                     # follow redirects
curl -X POST -H 'Content-Type: application/json' \
     -d '{"name":"alice"}' https://api/users # POST JSON
curl -fsSL https://get.example.com | bash    # fail-on-error, silent, follow

# wget: better for plain downloads / mirroring
wget https://example.com/file.tar.gz         # download to file
wget -c https://.../big.iso                   # continue a partial download
wget -r -np https://docs.example.com/         # recursive mirror
```

Rule of thumb: `curl` for *interacting with APIs* (custom methods, headers, bodies, and it streams to stdout for piping); `wget` for *downloading files* (robust resume `-c` and recursive `-r` mirroring). Always add `-f` to `curl` in scripts so an HTTP 500 produces a non-zero exit instead of silently saving an error page.

### Q18. [Theory] What is a symbolic link vs. a hard link?

Both create extra names for file data, but at different levels:

- A **hard link** is another directory entry pointing to the *same inode* (the same on-disk data). All hard links are equal; the data is freed only when the last link is removed. Hard links can't span filesystems or point to directories.
- A **symbolic (soft) link** is a tiny special file containing a *path* to another file. It can cross filesystems and link to directories, but breaks ("dangling") if the target is moved or deleted.

```bash
ln file.txt hardlink.txt       # hard link (same inode)
ln -s /opt/app/current app      # symlink (points to a path)
ls -li                          # -i shows inode numbers; hard links share one
readlink -f app                 # resolve a symlink to its real target
```

Symlinks are everywhere in deployments — e.g. `current → releases/2026-06-30` so a deploy is an atomic symlink swap.

## 🟡 Intermediate (3–7 yrs)

### Q19. [Theory] Explain signals in depth. What are SIGTERM, SIGKILL, SIGINT, SIGHUP, and SIGSTOP, and which can be caught?

Signals are asynchronous notifications the kernel delivers to a process. A process can install a *handler* to catch most of them, except two that the kernel enforces directly.

| Signal   | Num | Default action     | Catchable? | Typical use                         |
|----------|-----|--------------------|------------|-------------------------------------|
| SIGINT   | 2   | terminate          | yes        | Ctrl-C in the terminal              |
| SIGQUIT  | 3   | terminate + core   | yes        | Ctrl-\ ; JVM prints a thread dump   |
| SIGKILL  | 9   | terminate          | **no**     | force-kill a stuck process          |
| SIGTERM  | 15  | terminate          | yes        | polite shutdown request (default)   |
| SIGHUP   | 1   | terminate          | yes        | terminal closed; often "reload config" |
| SIGSTOP  | 19  | stop (pause)       | **no**     | suspend a process (Ctrl-Z = SIGTSTP)|
| SIGCONT  | 18  | continue           | yes        | resume a stopped process            |

`SIGKILL` and `SIGSTOP` are special: they cannot be caught, blocked, or ignored, which is why `kill -9` always works. `SIGHUP` historically meant "hangup" (terminal disconnected); daemons repurpose it to mean "reload configuration without restarting" (e.g. `kill -HUP $(pidof nginx)`). For the JVM, `SIGQUIT` (Ctrl-\) triggers a full thread dump to stdout — a great live-debugging trick.

### Q20. [Practical] How do you manage jobs — background, foreground, `nohup`, and `disown`?

The shell runs commands in the foreground by default (blocking your prompt). Job control lets you push work to the background and detach it from the terminal.

```bash
./long-task.sh &        # start in background, prints [1] <pid>
jobs                    # list jobs of this shell
fg %1                   # bring job 1 to the foreground
bg %1                   # resume a stopped job in the background
Ctrl-Z                  # SIGTSTP — suspend the foreground job
kill %1                 # signal a job by its job spec

# Survive logout / terminal close:
nohup ./server.sh &     # ignore SIGHUP; output → nohup.out
./server.sh & disown    # remove from shell's job table (no SIGHUP on exit)
```

```
foreground ──Ctrl-Z──▶ stopped ──bg──▶ background (running)
     ▲                                      │
     └──────────────── fg ──────────────────┘
```

`nohup` makes a process ignore `SIGHUP` so it survives the terminal closing; `disown` removes it from the shell's job list so the shell won't signal it on exit. For anything long-lived, prefer a real supervisor (`systemd` service, `tmux`/`screen`) over `nohup &`.

### Q21. [Coding] Write a script using `getopts` to parse `-f <file>`, `-v` (verbose flag), and `-n <count>`.

```bash
#!/usr/bin/env bash
set -euo pipefail

verbose=0
file=""
count=1

usage() { echo "usage: $0 -f <file> [-v] [-n <count>]" >&2; exit 1; }

while getopts ":f:vn:" opt; do
    case "$opt" in
        f) file="$OPTARG" ;;
        v) verbose=1 ;;
        n) count="$OPTARG" ;;
        \?) echo "unknown option: -$OPTARG" >&2; usage ;;
        :)  echo "option -$OPTARG needs an argument" >&2; usage ;;
    esac
done
shift $((OPTIND - 1))     # drop parsed options; "$@" now holds positionals

[[ -n "$file" ]] || usage
(( verbose )) && echo "file=$file count=$count remaining=$*"

for ((i = 1; i <= count; i++)); do
    echo "[$i] processing $file"
done
```

Notes: the leading `:` in `":f:vn:"` enables *silent* error handling so you can give custom messages; a letter followed by `:` (like `f:`) means that option takes an argument (in `$OPTARG`); `shift $((OPTIND-1))` discards the options so `"$@"` holds the leftover positional arguments.

### Q22. [Practical] Demonstrate `sed` for common substitutions and in-place edits.

`sed` is a stream editor that applies edits line-by-line. Its killer feature is substitution (`s/pattern/replacement/`).

```bash
# Replace first occurrence per line
sed 's/foo/bar/' file

# Replace ALL occurrences per line (g = global)
sed 's/foo/bar/g' file

# In-place edit, keeping a .bak backup
sed -i.bak 's/8080/9090/g' application.properties

# Delete matching lines
sed '/^#/d' config            # remove comment lines
sed '/^$/d' file              # remove blank lines

# Print only a range of lines (like a precise head/tail)
sed -n '10,20p' big.log

# Use a different delimiter when the pattern has slashes
sed 's#/old/path#/new/path#g' file
```

`-i` edits the file in place (use `-i.bak` to keep a safety copy — GNU sed). For multi-character/structured transformations, reach for `awk`; `sed` shines at simple find-and-replace across streams.

### Q23. [Practical] Demonstrate `awk` for field extraction and aggregation.

`awk` is a column-oriented mini-language: it splits each line into fields (`$1`, `$2`, …; `$0` is the whole line) and runs your program per line. It excels at whitespace/CSV columns and running totals.

```bash
# Print the 1st and 3rd whitespace-separated fields
awk '{print $1, $3}' data.txt

# Use a custom field separator (CSV)
awk -F',' '{print $2}' users.csv

# Filter rows then print a column
ps aux | awk '$3 > 50 {print $2, $11}'    # PIDs using >50% CPU

# Sum a column (e.g. bytes in field 10 of an access log)
awk '{sum += $10} END {print sum}' access.log

# Count occurrences (group-by) using an associative array
awk '{count[$1]++} END {for (k in count) print count[k], k}' access.log \
  | sort -rn | head
```

The structure is `pattern { action }`: a leading pattern (a condition or regex) gates whether the action runs, and the special `BEGIN`/`END` blocks run before/after all input. When you find yourself piping `grep | cut | sort` together, a single `awk` often does it more clearly.

### Q24. [Coding] Given an Nginx/Apache access log, find the top 10 IP addresses by request count using a one-liner.

```bash
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10
```

Step by step:

```
awk '{print $1}'   → extract the first field (client IP) from each line
sort               → group identical IPs together (uniq needs sorted input)
uniq -c            → collapse duplicates, prefixing each with its count
sort -rn           → sort by that count, reverse (-r) numeric (-n)
head -10           → keep the top 10
```

This `sort | uniq -c | sort -rn` idiom is the canonical "count and rank" pipeline and shows up constantly in real log triage. To filter to errors first, prepend `grep ' 500 '` or `awk '$9==500'`.

### Q25. [Practical] Explain `cut`, `sort`, `uniq`, `tr`, and `wc` with examples.

These are the small composable text tools that glue pipelines together.

```bash
# cut — slice columns by delimiter or character position
cut -d':' -f1 /etc/passwd        # usernames (field 1, delim :)
cut -c1-8 file                   # first 8 characters of each line

# sort — order lines
sort -u names.txt                # sort + dedupe
sort -t',' -k2 -n data.csv       # by 2nd CSV field, numerically
sort -k3 -rn -h sizes.txt        # human-numeric reverse (1K < 1M < 1G)

# uniq — collapse ADJACENT duplicates (so sort first!)
sort log | uniq -c               # count occurrences
sort log | uniq -d               # show only duplicated lines

# tr — translate/delete characters
echo "Hello" | tr 'a-z' 'A-Z'    # → HELLO
tr -d '\r' < dos.txt > unix.txt  # strip carriage returns
tr -s ' '                        # squeeze repeated spaces to one

# wc — count
wc -l file       # lines
wc -w file       # words
wc -c file       # bytes
```

The most-tested gotcha: **`uniq` only deduplicates *adjacent* lines**, so you almost always pipe `sort | uniq`. `cut` is great for fixed delimiters but can't handle quoted CSV fields — use `awk` or a real CSV tool for that.

### Q26. [Practical] What is `xargs` and why is it needed? How do you handle filenames with spaces safely?

Many programs take arguments on the command line, not on stdin. `xargs` reads items from stdin and turns them into arguments for a command — bridging the gap between piped output and argument-hungry tools.

```bash
# Without xargs, `find ... | rm` does nothing useful (rm ignores stdin)
find . -name '*.tmp' | xargs rm          # WRONG if names have spaces

# SAFE: NUL-separate to survive spaces/newlines in filenames
find . -name '*.tmp' -print0 | xargs -0 rm

# Run in parallel (4 at a time)
find . -name '*.log' -print0 | xargs -0 -P4 gzip

# Place args in the MIDDLE with a placeholder
ls *.txt | xargs -I{} cp {} /backup/{}.bak

# Batch sizes
echo {1..1000} | xargs -n 100 ./process   # 100 args per invocation
```

The danger: a filename containing a space or newline becomes *two* arguments and breaks (or worse, deletes the wrong file). The fix is the `-print0`/`-0` pair, which delimits items with NUL bytes that can't appear in filenames. Modern alternative: `find ... -exec rm {} +` avoids `xargs` entirely and is also space-safe.

### Q27. [Coding] Write a function-based Bash script with a reusable `log()` function and proper error handling.

```bash
#!/usr/bin/env bash
set -euo pipefail

readonly LOG_FILE="/tmp/deploy.$$.log"   # $$ = current PID, unique per run

log() {
    local level="$1"; shift
    printf '%s [%s] %s\n' "$(date '+%F %T')" "$level" "$*" | tee -a "$LOG_FILE"
}

cleanup() { log INFO "cleaning up"; rm -f /tmp/lock.$$ ; }
trap cleanup EXIT                # always runs on exit (success or error)
trap 'log ERROR "failed at line $LINENO"; exit 1' ERR

deploy() {
    local artifact="$1"
    [[ -f "$artifact" ]] || { log ERROR "missing $artifact"; return 1; }
    log INFO "deploying $artifact"
    # ... real work ...
}

main() {
    log INFO "start (pid $$)"
    deploy "${1:?usage: $0 <artifact>}"
    log INFO "done"
}

main "$@"
```

This shows the patterns interviewers reward: a `log()` helper with a `level` argument, `local` variables to avoid polluting global scope, `trap ... EXIT` for guaranteed cleanup, `trap ... ERR` to catch failures with `$LINENO`, and a `main "$@"` entry point so the script reads top-down.

### Q28. [Theory] What does `set -euo pipefail` do, and why is it considered a best practice?

It's the "unofficial strict mode" for Bash, turning silent failures into loud ones:

- **`set -e`** (errexit): exit immediately if any command returns non-zero (instead of plowing ahead). Saves you from `cd /nonexistent; rm -rf *` disasters.
- **`set -u`** (nounset): treat references to *unset* variables as an error. Catches typos like `$HOEM` and prevents `rm -rf "$DIR/"` from becoming `rm -rf /` when `DIR` is empty.
- **`set -o pipefail`**: a pipeline's exit status is the *first failing* command's, not just the last. Without it, `false | true` returns 0 and `set -e` never fires.

```bash
set -euo pipefail
IFS=$'\n\t'      # often added: safer word-splitting
```

Caveats worth mentioning: `-e` has surprising edge cases (it's suppressed in `if`/`&&`/`||` conditions and inside command substitution in subtle ways), and `-u` requires `${VAR:-default}` syntax for intentionally-optional vars. Despite quirks, it's the recommended starting point for any non-trivial script.

### Q29. [Theory] Explain users and groups. What's in /etc/passwd, /etc/shadow, and /etc/group?

Linux is multi-user; every user has a numeric **UID** and belongs to a primary **group** (GID) plus zero or more secondary groups. Three files back this:

```
/etc/passwd  →  user accounts (world-readable, NO passwords)
   alice:x:1001:1001:Alice,,,:/home/alice:/bin/bash
   └user └┘ └UID└GID └GECOS    └home dir   └login shell
         (x = password is in shadow)

/etc/shadow  →  hashed passwords + aging (root-only, mode 000/640)
   alice:$6$salt$hash:19500:0:99999:7:::

/etc/group   →  group definitions + memberships
   devs:x:1001:alice,bob
```

```bash
id alice                 # uid, gid, and group memberships
whoami                   # current username
groups                   # your groups
useradd -m -s /bin/bash bob   # create user + home
usermod -aG docker alice      # ADD to a group (-a is critical; -G alone REPLACES)
passwd alice                  # set/change password
sudo -u deploy ./task         # run as another user
```

Key gotcha: `usermod -G` *replaces* the secondary group list; you almost always want `-aG` to *append*. Passwords live hashed in `/etc/shadow` (readable only by root), while `/etc/passwd` is world-readable but holds no secrets.

### Q30. [Practical] How do you connect via SSH, set up key-based auth, and copy files with scp/rsync?

```bash
# Basic connection (default port 22)
ssh alice@server.example.com
ssh -p 2222 -i ~/.ssh/deploy_key alice@host    # custom port + identity

# Generate a key pair (ed25519 is the modern default)
ssh-keygen -t ed25519 -C "alice@laptop"
ssh-copy-id alice@host          # install your public key on the server

# Copy files
scp file.txt alice@host:/tmp/          # local → remote
scp alice@host:/var/log/app.log .      # remote → local
rsync -avz --progress src/ host:/dst/  # efficient sync (only deltas)
rsync -avz --delete src/ host:/dst/    # mirror (delete extras on dest)
```

The `~/.ssh/config` file removes repetitive flags:

```
Host prod
    HostName server.example.com
    User deploy
    Port 2222
    IdentityFile ~/.ssh/deploy_key
```

Then just `ssh prod`. Key-based auth (public key on the server's `~/.ssh/authorized_keys`, private key kept secret with `chmod 600`) is both more secure and scriptable than passwords. For large/incremental transfers prefer `rsync` — it copies only changed blocks and can resume.

### Q31. [Practical] What network tools do you use to inspect connections and sockets? Why is `ss` preferred over `netstat`?

`ss` (socket statistics) is the modern replacement for the deprecated `netstat`; it reads `/proc` faster and supports richer filters.

```bash
ss -tlnp            # TCP, Listening, Numeric ports, show Process (needs sudo)
ss -tunap           # TCP+UDP, all states, numeric, with PID
ss -s               # summary counts by state
ss state established '( dport = :443 )'   # filtered query

# What's listening on port 8080? (who's hogging my port)
ss -tlnp | grep ':8080'
lsof -i :8080       # alternative: list the process holding the port

# Legacy equivalents (still seen on older boxes)
netstat -tlnp
```

`netstat` is deprecated and missing on minimal modern images, while `ss` is faster and the expected answer in 2026. Common interview task: "a service won't start because the port is in use" → `ss -tlnp | grep :PORT` (or `lsof -i :PORT`) reveals the culprit PID.

### Q32. [Practical] How do you do DNS lookups from the command line? Compare `dig`, `nslookup`, and `host`.

```bash
dig example.com                 # full DNS answer (A records)
dig +short example.com          # just the IP(s)
dig example.com MX              # mail servers
dig @8.8.8.8 example.com        # query a specific resolver
dig +trace example.com          # follow delegation from the root
dig -x 93.184.216.34            # reverse lookup (PTR)

host example.com                # concise, human-friendly
nslookup example.com            # interactive-ish, older but ubiquitous
```

`dig` is the power tool — it shows the full answer/authority/additional sections, TTLs, and supports `+trace` to debug delegation. `host` is the quick one-liner. `nslookup` is older and less precise but present everywhere. For debugging "it works by IP but not by name" issues, also check `/etc/resolv.conf` (configured resolvers) and `/etc/hosts` (static overrides that bypass DNS).

### Q33. [Practical] How do you test connectivity to a remote port without a browser? Use `nc`, `telnet`, and `curl`.

```bash
# nc (netcat) — versatile TCP/UDP tool
nc -zv host 5432            # -z scan (no data), -v verbose: is the port open?
nc -zv host 20-25          # scan a range
nc -lvp 9000               # listen on 9000 (quick test server)

# telnet — old but handy for a raw line-oriented check
telnet smtp.example.com 25 # connect & speak the protocol by hand

# curl — application-layer reachability
```

When a service "can't reach the database," `nc -zv db-host 5432` instantly distinguishes a *network/firewall* problem (port closed/filtered) from an *application* problem (port open but app rejecting). `telnet host port` is the lowest-common-denominator on boxes without `nc`. Add `timeout 5` in front to avoid hanging on filtered ports.

### Q34. [Theory] Compare common package managers: apt, dnf/yum, and the role of dpkg/rpm underneath.

Package managers install software and resolve dependencies. There are two big families:

| Family       | Distros            | High-level tool | Low-level | Package |
|--------------|--------------------|-----------------|-----------|---------|
| Debian/Ubuntu| Debian, Ubuntu     | `apt`           | `dpkg`    | `.deb`  |
| Red Hat      | RHEL, Fedora, Rocky| `dnf` (was yum) | `rpm`     | `.rpm`  |

```bash
# Debian / Ubuntu
sudo apt update                  # refresh package index
sudo apt install nginx           # install + resolve deps
sudo apt upgrade                 # upgrade installed packages
apt list --installed | grep jdk
dpkg -l | grep nginx             # query (low-level)

# RHEL / Fedora / Rocky
sudo dnf install nginx
sudo dnf update
rpm -qa | grep nginx             # query installed
rpm -qf /usr/sbin/nginx          # which package owns this file?
```

The high-level tools (`apt`, `dnf`) handle *dependency resolution and repositories*; the low-level tools (`dpkg`, `rpm`) install a single package file and back the database. In 2026, also expect questions on `snap`/`flatpak` (sandboxed cross-distro apps) and language-specific managers, but the apt-vs-dnf split is the core knowledge.

### Q35. [Practical] How do you schedule recurring jobs with cron? Explain the five time fields.

`cron` runs commands on a schedule defined by a crontab. Each line has five time fields plus a command.

```
┌───────── minute        (0–59)
│ ┌─────── hour          (0–23)
│ │ ┌───── day of month  (1–31)
│ │ │ ┌─── month         (1–12)
│ │ │ │ ┌─ day of week   (0–7, 0 & 7 = Sunday)
│ │ │ │ │
* * * * *  command-to-run
```

```bash
crontab -e          # edit YOUR crontab
crontab -l          # list it

# Examples
0 2 * * *      /opt/backup.sh                 # daily at 02:00
*/15 * * * *   /usr/bin/healthcheck            # every 15 minutes
0 9 * * 1-5    /opt/report.sh                  # weekdays at 09:00
@reboot        /opt/start-agent.sh             # once at boot
0 0 1 * *      /opt/monthly.sh                 # 1st of each month
```

Critical gotchas to mention: cron runs with a **minimal environment** (sparse `PATH`, no profile), so use absolute paths and set variables explicitly; always redirect output (`>> /var/log/job.log 2>&1`) or cron emails it; and on systemd distros, **`systemd timers`** are the modern alternative offering logging, dependencies, and randomized delays.

### Q36. [Theory] What is systemd, and how do you manage a service with systemctl?

`systemd` is the init system (PID 1) and service manager on virtually all modern Linux distros. It starts/stops services ("units"), tracks their state and dependencies, captures their logs into the **journal**, and restarts crashed processes.

```bash
sudo systemctl start myapp        # start now
sudo systemctl stop myapp
sudo systemctl restart myapp
sudo systemctl reload myapp       # reload config without full restart (if supported)
systemctl status myapp            # state, PID, recent log lines
sudo systemctl enable myapp       # auto-start on boot
sudo systemctl disable myapp
systemctl is-active myapp         # scriptable check
systemctl list-units --type=service --state=running
sudo systemctl daemon-reload      # after editing a unit file
```

A minimal unit file at `/etc/systemd/system/myapp.service`:

```ini
[Unit]
Description=My Java App
After=network.target

[Service]
ExecStart=/usr/bin/java -jar /opt/app/app.jar
User=appuser
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

The pair to remember: **`start`/`stop` act now**, **`enable`/`disable` control boot behavior** — enabling does not start it immediately, and starting does not survive reboot. After editing a unit, run `systemctl daemon-reload`.

### Q37. [Practical] How do you read service logs with journalctl?

`journalctl` queries systemd's structured, indexed journal — replacing scattered grep-through-files for systemd services.

```bash
journalctl -u myapp                 # all logs for one service
journalctl -u myapp -f              # follow live (like tail -f)
journalctl -u myapp -n 100          # last 100 lines
journalctl -u myapp --since "1 hour ago"
journalctl -u myapp --since today --until "10:00"
journalctl -u myapp -p err          # priority err and worse
journalctl -b                       # logs since the last boot
journalctl -b -1                    # the PREVIOUS boot (post-crash forensics)
journalctl -k                       # kernel messages (dmesg equivalent)
journalctl --disk-usage             # how big is the journal?
```

Traditional text logs still live in `/var/log` (`/var/log/syslog`, `/var/log/messages`, app-specific files) and are read with `tail -f`, `less`, `grep`, and `zgrep` (for rotated `.gz` files). For systemd services, `journalctl -u <service>` is the first stop; `-b -1` to see what happened *before* a crash/reboot is a pro move.

### Q38. [Theory] What does `nice` / `renice` do, and how does it relate to process scheduling?

`nice` adjusts a process's **niceness** — a scheduling priority hint from **-20 (highest priority / least nice)** to **+19 (lowest priority / most nice)**. A "nicer" process voluntarily yields more CPU to others. Default is 0; only root can set negative (higher-priority) values.

```bash
nice -n 10 ./batch-job.sh      # start with reduced priority (+10)
renice -n 5 -p 12345           # change priority of a RUNNING process
renice -n -5 -p 12345          # raise priority (needs root)
top                            # the NI column shows niceness, PR the kernel priority
```

```
  -20  ◀──────────── niceness ────────────▶  +19
 higher priority          0           lower priority
 (grabs more CPU)      default      (yields to others)
```

Use it to keep a CPU-heavy batch job from starving interactive or latency-sensitive services. For *I/O* priority there's a separate tool, `ionice`. Niceness is a *hint* to the scheduler, not a hard cap — for hard limits use cgroups (`systemd` `CPUQuota=`).

### Q39. [Practical] A production server shows high load average. Walk through how you diagnose the root cause.

Start by separating *load* (run-queue length + uninterruptible tasks) from *CPU saturation* — high load with low CPU usually means I/O wait or blocked tasks.

```bash
uptime                 # load over 1/5/15 min; compare to core count (nproc)
top    # or htop       # %us user, %sy system, %wa I/O-wait, %id idle; sort by CPU/MEM
vmstat 1 5             # r (run queue), b (blocked), wa, si/so (swap I/O)
mpstat -P ALL 1        # per-core: is ONE core pegged or all of them?
iostat -xz 1           # %util, await per disk → spot disk saturation
pidstat 1              # per-process CPU/IO over time
```

Decision flow:

```
load high?
 ├─ %us high  → CPU-bound: find the process (top → P), profile it
 ├─ %sy high  → kernel/syscalls: context switches, interrupts, forking storm
 ├─ %wa high  → I/O-bound: iostat shows the disk; find the heavy process (iotop)
 └─ %id high but load high → many tasks in 'D' (uninterruptible): `ps -eo stat`
                              look for blocked-on-I/O or NFS hangs
```

The key insight: **load average counts both runnable *and* uninterruptible (D-state) tasks**, so a stuck NFS mount or saturated disk inflates load even when CPUs are idle. Always correlate `uptime` load against `nproc` (a load of 4 is fine on 8 cores, alarming on 2).

### Q40. [Practical] A Java service is consuming all the memory on the box. How do you investigate?

Distinguish *which* process, *what kind* of memory (heap vs. off-heap vs. page cache), and whether the kernel OOM-killer is involved.

```bash
free -h                          # total/used/free, buffers/cache, swap
ps aux --sort=-%mem | head       # top memory consumers (RSS)
cat /proc/<pid>/status | grep -i vm   # VmRSS, VmSwap for the JVM
pmap -x <pid> | tail             # memory map breakdown
dmesg -T | grep -i 'killed process'   # did the OOM killer strike?
journalctl -k | grep -i oom
```

For the JVM specifically:

```bash
jcmd <pid> GC.heap_info          # heap usage
jcmd <pid> VM.native_memory summary   # if NativeMemoryTracking enabled (off-heap)
jmap -histo:live <pid> | head    # live object histogram (triggers a GC)
kill -3 <pid>                    # SIGQUIT → thread dump to stdout/log
```

Crucial nuances: `free`'s "used" includes nothing scary if it's **buffers/cache** (reclaimable) — look at the *available* column, not *free*. A Java process's `RSS` can exceed `-Xmx` because of metaspace, thread stacks, direct `ByteBuffers`, and JIT code cache — so "container OOM-killed but heap looked fine" points to *off-heap* growth. Check `dmesg`/`journalctl -k` for the OOM killer's verdict, which names the victim PID and the memory at the time.

### Q41. [Practical] Disk is full in production. Walk through finding and safely freeing space.

```bash
df -h                            # which filesystem is full?
df -i                            # OR is it INODES, not bytes?

# Find the biggest consumers on the full mount
du -h --max-depth=1 / 2>/dev/null | sort -rh | head
du -ah /var/log | sort -rh | head -20

# The classic trap: space "missing" because of deleted-but-open files
lsof +L1 | grep deleted          # files unlinked but still held by a process
lsof / | grep deleted
```

Safe remediation, in order of preference:

1. **Compress or rotate logs** rather than delete blindly: `logrotate -f /etc/logrotate.conf`, or `gzip` old logs.
2. **Truncate, don't delete, an open log file**: `: > /var/log/huge.log` (or `truncate -s 0`) frees space *and* keeps the file descriptor valid for the writing process. Deleting it leaves the space held until restart.
3. **Clean package caches**: `apt clean` / `dnf clean all`, old kernels, `journalctl --vacuum-size=200M`.
4. For deleted-but-open files with no rotation, **restart the holding process** to release the descriptor.

The two signature gotchas to articulate: a deleted file still open by a process keeps consuming space (visible only via `lsof | grep deleted`), and an inode-exhausted filesystem reports "No space left on device" with gigabytes of bytes free (`df -i` reveals it; cause is usually millions of tiny files).

### Q42. [Coding] Write a robust health-check script that probes an HTTP endpoint, retries, and exits non-zero on failure for use in a systemd/monitoring context.

```bash
#!/usr/bin/env bash
set -euo pipefail

URL="${1:?usage: $0 <url> [retries] [timeout]}"
RETRIES="${2:-3}"
TIMEOUT="${3:-5}"

check() {
    local code
    # -f → non-zero on HTTP >= 400; -s silent; -o discard body
    code=$(curl -fsS --max-time "$TIMEOUT" -o /dev/null \
                -w '%{http_code}' "$URL") || return 1
    [[ "$code" == 2?? ]]      # accept any 2xx
}

for ((attempt = 1; attempt <= RETRIES; attempt++)); do
    if check; then
        echo "OK  $URL (attempt $attempt)"
        exit 0
    fi
    echo "WARN $URL failed (attempt $attempt/$RETRIES)" >&2
    sleep $(( attempt * 2 ))     # linear backoff: 2s, 4s, 6s...
done

echo "CRITICAL $URL unhealthy after $RETRIES attempts" >&2
exit 2          # non-zero → systemd/monitor marks the check failed
```

Interview-worthy details: `curl -f` turns HTTP 5xx into a non-zero exit (otherwise curl "succeeds" on an error page), `--max-time` bounds hangs, a `2??` glob validates the status class, backoff avoids hammering a struggling service, and distinct exit codes (`0` ok, `2` critical) integrate cleanly with Nagios/systemd `ExecStartPost`/Kubernetes probes.

### Q43. [Theory] Explain setuid, setgid, and the sticky bit. Why is `/usr/bin/passwd` setuid and `/tmp` sticky?

These are three *special* permission bits beyond the usual rwx, shown in the `x` slot of `ls -l` (as `s`, `s`, `t`):

- **setuid (4000)** on an executable: it runs with the privileges of the file's **owner**, not the caller. `/usr/bin/passwd` is owned by root and setuid so an ordinary user can update their hashed password in root-only `/etc/shadow` — without a general root shell.
- **setgid (2000)** on an executable runs with the group's privileges; on a *directory*, new files inherit the directory's **group** (handy for shared team folders).
- **sticky bit (1000)** on a *directory*: only a file's **owner** (or root) may delete/rename it, even if others have write permission. `/tmp` is world-writable but sticky so users can't delete each other's temp files.

```bash
ls -l /usr/bin/passwd       # -rwsr-xr-x  → the 's' is setuid
ls -ld /tmp                 # drwxrwxrwt  → trailing 't' is the sticky bit
chmod u+s prog              # set setuid    (octal 4755)
chmod g+s shared_dir        # set setgid    (octal 2775)
chmod +t shared_tmp         # set sticky    (octal 1777)
find / -perm -4000 -type f 2>/dev/null   # AUDIT: list all setuid binaries
```

Security angle interviewers love: setuid-root binaries are a prime privilege-escalation target, so you audit them (`find / -perm -4000`), minimize them, and treat any *writable* setuid binary as critical. A capital `S`/`T` instead of `s`/`t` means the special bit is set but the underlying `x` is **not** — usually a misconfiguration.

### Q44. [Practical] How do you capture and inspect network traffic with tcpdump for troubleshooting?

`tcpdump` captures packets on an interface using BPF filters — the go-to when you need to *prove* what's actually on the wire.

```bash
tcpdump -i eth0                       # live capture on eth0
tcpdump -i any -n port 443            # any iface, no DNS resolve, only :443
tcpdump -i eth0 host 10.0.0.5 and port 5432   # filter by host AND port
tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'   # SYN/RST only
tcpdump -i eth0 -c 100 -w capture.pcap         # write 100 pkts to a file
tcpdump -nr capture.pcap                        # read a saved pcap
tcpdump -i eth0 -A port 80            # print packet payload as ASCII (HTTP)
```

Practical workflow: capture to a `.pcap` on the server with a tight filter (to limit volume), then pull it down and open it in **Wireshark** for deep analysis. Always **filter aggressively** (`host`/`port`) on busy links so you don't drown in packets or impact the box. Typical wins: confirming a TCP handshake completes (SYN → SYN/ACK → ACK), spotting `RST` floods (connection refused/firewall), or diagnosing slow responses by timestamps. Note it usually needs root/`CAP_NET_RAW`.

### Q45. [Practical] Explain how to debug "the service started but isn't reachable" end-to-end.

Work the layers from the process outward — each command rules out one layer:

```bash
# 1. Is the process actually running?
systemctl status myapp
ps aux | grep myapp

# 2. Is it LISTENING, and on which address/port?
ss -tlnp | grep myapp        # 127.0.0.1:8080 vs 0.0.0.0:8080 matters a LOT!

# 3. Local reachability (bypasses network/firewall)
curl -v http://127.0.0.1:8080/health

# 4. Firewall blocking the port?
sudo iptables -L -n         # or: nft list ruleset
sudo firewall-cmd --list-all # firewalld
sudo ufw status              # ufw

# 5. From a remote box: is the port open across the network?
nc -zv server-ip 8080
curl -v http://server-ip:8080/health

# 6. Name resolution (works by IP but not by name)?
dig service.example.com
cat /etc/hosts /etc/resolv.conf
```

The single most common root cause: the service is bound to **`127.0.0.1`** (loopback only) instead of **`0.0.0.0`** (all interfaces), so it works locally but is unreachable from other hosts — `ss -tlnp` exposes this instantly. After that, the usual suspects are **firewall rules** (iptables/nftables/firewalld/ufw or a cloud security group), then **DNS**. Going layer-by-layer with one command each turns a vague "it's down" into a precise finding.

### Q46. [Behavioral] Tell me about a time a Linux/shell issue caused a production incident. How did you handle it?

Use a STAR structure and emphasize disciplined troubleshooting over heroics.

- **Situation/Task**: Be concrete — e.g. "Our payments service began OOM-killing every few hours after a deploy; on-call paged at 2 a.m."
- **Action**: Show methodical diagnosis, not flailing. "I confirmed via `journalctl -k | grep -i oom` that the kernel OOM-killer was terminating the JVM. `ps aux --sort=-%mem` and `/proc/<pid>/status` showed RSS far above `-Xmx`, pointing to *off-heap* growth. `pmap` and native memory tracking traced it to a leak of direct `ByteBuffers` introduced by the new release. - **Result**: Quantify and reflect. "MTTR was 40 minutes; we added a Grafana panel for container RSS vs. heap and a pre-deploy native-memory check so off-heap regressions are caught in staging."

What interviewers listen for: a clear hypothesis-driven path (logs → metrics → root cause), choosing the *safe* action under pressure (rollback + truncate vs. risky deletes), and a follow-up that prevents recurrence (monitoring, runbook, guardrail). Owning a mistake honestly scores higher than a flawless-hero narrative.

### Q47. [Coding] Write a one-liner pipeline that reports the top 5 directories by size under a path, human-readable.

```bash
du -h --max-depth=1 /var 2>/dev/null | sort -rh | head -6
```

Explanation:

```
du -h --max-depth=1 /var   → size of /var and each immediate child, human units
2>/dev/null                → suppress "permission denied" noise
sort -rh                   → reverse, human-numeric sort (so 2G > 900M > 50K)
head -6                    → 5 subdirs + the /var total line itself
```

The load-bearing flag is **`sort -h`** (human-numeric): it correctly orders `1K < 1M < 1G` instead of sorting them lexically (where "900M" would beat "2G"). Pair with `du -ah` and a larger `head` to drill into individual files once you've found the heavy directory.

### Q48. [Theory] Explain what happens, step by step, from typing a command to seeing output — covering fork/exec, file descriptors, and the process lifecycle.

This question tests whether you understand the OS underneath the shell:

```
1. READ/PARSE  The shell reads the line, performs expansions (variables,
               globbing, command substitution), and splits it into words.
2. BUILTIN?    If it's a builtin (cd, export), the shell runs it itself.
               Otherwise it resolves the command via $PATH.
3. fork()      The shell clones itself → a child process (copy-on-write
               address space; the child is a near-duplicate of the parent).
4. (setup)     In the child, the shell wires up redirections/pipes by
               dup2()'ing file descriptors (e.g. fd 1 → a pipe or a file).
5. execve()    The child REPLACES its image with the new program; its PID
               stays the same but the code/data/heap are now the new binary.
6. (parent)    The shell calls wait()/waitpid() to block until the child
               exits (unless backgrounded with &).
7. EXIT        The child runs, writes to stdout/stderr, returns an exit code,
               and exits; the kernel keeps a zombie entry until the parent
               reaps it via wait(), which yields $?.
```

```
 shell ──fork()──▶ child (copy) ──dup2() fds──▶ ──execve(ls)──▶ runs ls
   │                                                              │
   └────────────────── wait() blocks ◀──── exit code ◀───────────┘
```

Deep points to land: `fork`+`exec` is *two* syscalls (clone, then replace), which is why redirection/pipe setup happens *between* them in the child; copy-on-write makes `fork` cheap; a process that exits before its parent `wait()`s becomes a **zombie** (just an exit-status entry), and if the parent dies first the child is **reparented to PID 1** (init/systemd) which reaps it. Pipelines are multiple forked children whose fds are joined with `pipe()`.

### Q49. [Theory] Explain the OOM killer: how Linux decides what to kill, overcommit, and how to protect critical processes.

When the kernel can't satisfy a memory allocation and reclaim fails, the **OOM (out-of-memory) killer** picks a process to terminate to recover memory.

- **Overcommit**: by default Linux lets processes allocate more virtual memory than physically exists (`vm.overcommit_memory`), betting they won't touch all of it. When that bet fails under real pressure, the OOM killer fires. This is why `malloc`/JVM reservation can "succeed" yet a later page fault triggers a kill.
- **Victim selection**: each process has an `oom_score` (in `/proc/<pid>/oom_score`) derived mainly from its memory footprint, adjustable via `oom_score_adj` (-1000 to +1000). The kernel kills the highest score — typically the biggest memory hog, which is often your JVM.

```bash
cat /proc/<pid>/oom_score          # current score (higher = killed first)
echo -500 > /proc/<pid>/oom_score_adj   # bias AWAY from being killed
dmesg -T | grep -i 'oom\|killed process'  # post-mortem: who got killed & why
```

Protection strategies to discuss: set `OOMScoreAdjust=` in the systemd unit for critical daemons; use **cgroup v2 `memory.max`/`memory.high`** to contain a runaway process *before* it threatens the whole box (so the cgroup, not the system, OOMs); disable swap thrash awareness; and for the JVM, size `-Xmx` plus off-heap headroom *below* the container limit so the JVM hits its own `OutOfMemoryError` (recoverable, with a heap dump) rather than getting `SIGKILL`ed with no diagnostics.

### Q50. [Practical] How would you trace what a misbehaving binary is actually doing with strace/ltrace and the /proc filesystem?

When logs aren't enough, observe the process at the syscall boundary:

```bash
strace -f -p <pid>                 # attach; -f follows forked threads
strace -e trace=network ./app       # only network syscalls
strace -e trace=openat -f ./app     # which files does it try to open?
strace -T -tt -p <pid>              # timestamps + time spent per syscall (find slow ones)
strace -c -p <pid>                  # summary: syscall counts & time (great first pass)
ltrace -p <pid>                     # library calls (e.g. malloc, libssl) instead of syscalls
```

`/proc/<pid>` is a live X-ray of any process without attaching a tracer:

```bash
ls -l /proc/<pid>/fd               # every open file descriptor (sockets, files, pipes)
cat   /proc/<pid>/limits           # ulimits in effect (e.g. max open files)
cat   /proc/<pid>/status           # VmRSS, threads, state, UID
readlink /proc/<pid>/cwd /proc/<pid>/exe   # working dir & the binary path
cat   /proc/<pid>/environ | tr '\0' '\n'   # the process's environment
cat   /proc/<pid>/maps             # memory mappings (libs, heap, stack)
```

Classic finds: `strace` revealing an `ENOENT` on a missing config file, `EACCES` on a permission problem, or the process spinning on `EAGAIN`/`poll`; `/proc/<pid>/fd` showing it's hit the open-file-descriptor limit (`Too many open files`). Note `strace` adds significant overhead (every syscall traps), so use `-c` for a quick profile and avoid attaching to latency-critical production processes longer than necessary; for low-overhead production tracing in 2026, prefer **eBPF** tools (`bpftrace`, `bcc`, `perf`).

### Q51. [Behavioral] You're mentoring engineers who reach for risky shell commands under pressure. How do you raise the team's operational discipline?

This probes leadership, blameless culture, and turning incidents into durable improvements.

- **Set guardrails, not just rules.** Codify dangerous operations into reviewed, idempotent scripts and runbooks so people aren't improvising `rm -rf` at 3 a.m. Make the safe path the easy path: tested rollback scripts, `--dry-run` flags, confirmation prompts on destructive actions, and read-only-by-default access with break-glass escalation.
- **Teach the reasoning, not the incantation.** Pair on incidents and explain *why* (`SIGTERM` before `SIGKILL`, truncate vs. delete an open log, `df -i` for inodes) so judgment generalizes. Encourage "verify before you destroy": `ls` the glob before `rm` it, snapshot before you mutate, and prefer reversible actions.
- **Build a blameless feedback loop.** Run blameless post-incident reviews focused on systemic gaps (missing alert, no rollback, unsafe default) rather than the individual. Track action items to completion. When someone narrowly avoids disaster, celebrate the catch and fold it into the runbook.
- **Reduce blast radius systemically.** Least-privilege sudo, separate prod credentials, cgroup/quota limits, staged rollouts, and chaos/game-day drills so the first time someone handles a scenario isn't during a real outage.

Strong answers show you measure the outcome (fewer incidents, faster MTTR, runbook coverage) and model the calm, methodical behavior you want the team to copy — culture is set by what senior engineers do under pressure, not what they say.

### Q52. [Theory] Compare cgroups and namespaces — the Linux primitives that make containers possible — and how they relate to what you tune in production.

Containers are not a kernel feature; they're a *combination* of two independent Linux mechanisms:

- **Namespaces** provide *isolation* — they give a process its own private view of a global resource. The main ones: **PID** (its own process tree, so the container's app is PID 1), **mount** (its own filesystem view), **network** (its own interfaces, ports, routing), **UTS** (hostname), **IPC**, **user** (UID mapping — container root ≠ host root), and **cgroup**. This is *what a process can see*.
- **cgroups (control groups)** provide *limits and accounting* — they constrain *how much* a group of processes may consume: `memory.max`, `cpu.max`/`CPUQuota`, `pids.max`, I/O weight. This is *what a process can use*. cgroup **v2** (the unified hierarchy, standard in 2026) is what `systemd` and container runtimes drive.

```
container = namespaces (isolation: what you SEE)
          + cgroups    (limits:    what you USE)
          + a root filesystem image + a runtime (runc/containerd)
```

```bash
systemd-cgls                         # tree of cgroups and their processes
systemctl set-property myapp.service MemoryMax=2G CPUQuota=150%
cat /sys/fs/cgroup/.../memory.max    # cgroup v2 memory limit
lsns                                 # list namespaces on the system
nsenter -t <pid> -n ss -tlnp         # enter a container's NET namespace from the host
```

Where this bites in production: a JVM that reads host CPU/memory instead of the cgroup limit will size its thread pools and heap wrong — modern JDKs are *container-aware* (`UseContainerSupport`) and read cgroup v2 limits, but you verify with `nproc`/`/sys/fs/cgroup`. A "container OOM-killed" event is the *cgroup's* `memory.max` being hit, not the host running out — and `nsenter` lets you debug a container's network namespace from the host when you can't get a shell inside it.

#### Q53. [Theory] What actually is a file in Linux, and what does "everything is a file" mean concretely?

In Linux a "file" is fundamentally an **inode** plus a way to talk to it through a uniform read/write/ioctl interface. A directory entry (a *name*) points to an inode; the inode holds the metadata (mode, owner, timestamps, link count, and pointers to data blocks) but *not* the name. "Everything is a file" means the kernel exposes wildly different things behind the same file-descriptor API:

- **Regular files** — bytes on a filesystem.
- **Directories** — special files mapping names → inode numbers.
- **Device files** (`/dev/sda`, `/dev/null`) — character/block devices; reads/writes go to a driver.
- **Pipes & FIFOs** — in-kernel byte buffers between processes.
- **Sockets** — network/IPC endpoints.
- **Pseudo-filesystems** (`/proc`, `/sys`) — kernel data structures rendered as readable text.

```bash
ls -i file            # show the inode number a name points to
stat -c '%i %h' file  # inode number and hard-link count
```

The power is uniformity: the same `read(2)`/`write(2)`/`close(2)` syscalls work on a TCP socket, a keyboard, a disk file, and `/proc/meminfo`. The *name* is just a label in a directory; the **inode** is the file. Deleting the last name (link count → 0) with no open descriptor is what actually frees the data.

#### Q54. [Theory] Walk through what an inode contains and why the filename is not part of it.

An inode is the filesystem's per-file record. It stores:

- File **type** and **permission bits** (the mode).
- **Owner UID** and **group GID**.
- **Size** in bytes.
- **Timestamps** — `atime` (last access), `mtime` (last content change), `ctime` (last inode/metadata change). Note there is no true "creation" time in classic ext-family inodes, though ext4 added `crtime`.
- **Link count** — how many directory entries (hard links) reference this inode.
- **Block pointers** — direct/indirect pointers (or, on ext4/xfs, extents) to the data blocks.

Crucially, the **name lives in the directory**, not the inode. A directory is just a special file whose contents are `(name → inode number)` pairs. This separation is *why* hard links work (multiple names, one inode), why renaming within a filesystem is atomic and cheap (rewrite a directory entry, no data moves), and why `rm` is really `unlink(2)` — it removes a name and decrements the link count; the data is freed only when the count hits zero *and* no process holds the file open.

```bash
df -i                 # inode usage per filesystem — can exhaust independently of bytes
stat file             # dumps the inode fields in human form
```

#### Q55. [Theory] What is a file descriptor really, and how do the three per-process tables fit together?

A file descriptor is a small non-negative **integer index** into a per-process table. Three layers sit behind it:

```
process fd table        system open file table        inode table
[0] ───▶  open file entry ──▶  (offset, flags, mode) ──▶ inode (the file)
[1] ───▶  open file entry ──▶  ...                  ──▶ inode
[2] ───▶  ...
```

1. **Per-process descriptor table** — maps `fd` → an entry in the open file table. Each `fork` copies this table; each `exec` keeps it (unless `FD_CLOEXEC` is set).
2. **System-wide open file table** — each `open(2)` creates an entry holding the current **file offset** and the status flags (`O_APPEND`, `O_NONBLOCK`, …). Two `open`s of the same path get *separate* entries (independent offsets).
3. **Inode table** — the actual file. Many open-file entries can point to one inode.

This three-table model explains key behaviors: `dup2(oldfd, newfd)` makes two descriptors share *one* open-file entry, so they share the offset — that is exactly how shell redirection (`2>&1`) and pipes are wired. After `fork`, parent and child share open-file entries (same offset), which is why both writing to the same redirected file interleave correctly with `O_APPEND`.

#### Q56. [Practical] Explain how the shell expands a command line, in order. Why does quoting change globbing and word-splitting?

The shell performs expansions in a **fixed order** before it ever runs the command. Getting the order right explains most "why didn't my variable expand / why did my glob not match" puzzles:

1. **Brace expansion** — `{a,b}` → `a b`, `{1..3}` → `1 2 3` (purely textual, happens first).
2. **Tilde expansion** — `~` → `$HOME`, `~user` → that user's home.
3. **Parameter/variable expansion** — `$VAR`, `${VAR:-default}`.
4. **Command substitution** — `$(cmd)` / `` `cmd` ``.
5. **Arithmetic expansion** — `$(( 2 + 2 ))`.
6. **Word splitting** — the results of steps 3–5 are split on `$IFS` (default space/tab/newline). **Quoting suppresses this.**
7. **Filename (glob) expansion** — `*`, `?`, `[...]` are matched against the filesystem. **Quoting suppresses this too.**
8. **Quote removal** — the quote characters themselves are stripped.

```bash
files=$(ls)            # captures output
echo $files            # word-split + globbed  (each token separate, * expands)
echo "$files"          # quoted: one string, no splitting, no globbing
echo {dev,test}.log    # brace → dev.log test.log  (before globbing)
```

The load-bearing rule: **word splitting and globbing happen *after* variable expansion, so an unquoted `$VAR` containing spaces or `*` gets re-split and re-globbed.** That is why "always quote your variables" is the cardinal Bash rule — `"$VAR"` freezes the value after step 5 and skips 6 and 7.

#### Q57. [Theory] What is the difference between a shell builtin, a function, an alias, and an external command — and how does the shell resolve which to run?

When you type a word, Bash resolves it in a defined precedence order:

1. **Aliases** (only in interactive shells, expanded first, purely textual).
2. **Functions and builtins** — keywords like `if` first; then functions; then **builtins** (`cd`, `echo`, `export`, `read`, `[`, `pwd`).
3. **External commands** found by searching `$PATH` left-to-right (then cached in a hash table).

```bash
type -a echo          # shows EVERY match: builtin AND /usr/bin/echo
command -v cd         # how 'cd' resolves (a builtin)
which java            # external only — searches PATH (doesn't see builtins!)
enable -n echo        # disable the builtin so the external one is used
\ls                   # leading backslash bypasses an alias
```

Why it matters: `cd` *must* be a builtin — an external `cd` would `chdir` in a child process and the parent shell's directory wouldn't change. `which` only looks at `$PATH`, so it lies about builtins and functions; prefer `type -a` / `command -v` to know what will *actually* execute. Bash also caches PATH lookups (`hash`), which is why a freshly installed binary sometimes isn't found until `hash -r`.

#### Q58. [Theory] What is the page cache, and why does `free` show almost no "free" memory on a healthy server?

Linux uses otherwise-idle RAM as a **page cache**: copies of disk blocks (file contents) kept in memory so repeat reads are served without hitting the disk, and writes are buffered before flushing. This cache is **reclaimable on demand** — the kernel evicts clean cache pages instantly when a process needs the memory.

```bash
free -h
#               total   used   free   shared  buff/cache  available
# Mem:           31Gi   8Gi    300Mi   200Mi   23Gi        22Gi
```

The number that matters is **`available`**, not `free`. `free` ≈ truly unused RAM (which a good OS keeps tiny — empty RAM is wasted RAM); `available` is what an application could get *including* reclaimable cache. So 300 MiB "free" with 22 GiB "available" is perfectly healthy — the kernel has filled RAM with cache and will give it back when asked. The interview trap is reading the `free` column and concluding the box is out of memory.

```bash
sync; echo 3 > /proc/sys/vm/drop_caches   # drop caches (test/diagnostic only!)
```

`buff/cache` collapses buffers (block-device metadata) and the page cache. Dirty (not-yet-written) pages are flushed by the kernel's writeback threads governed by `vm.dirty_ratio` / `dirty_background_ratio`.

#### Q59. [Coding] Write a Bash snippet that safely creates a temporary file/dir and guarantees cleanup, and explain why `mktemp` beats hand-rolled names.

```bash
#!/usr/bin/env bash
set -euo pipefail

# Create a private temp dir with an unpredictable name (mode 700)
workdir="$(mktemp -d "${TMPDIR:-/tmp}/myjob.XXXXXXXX")"
tmpfile="$(mktemp "${TMPDIR:-/tmp}/myjob.XXXXXXXX")"

cleanup() { rm -rf -- "$workdir" "$tmpfile"; }
trap cleanup EXIT INT TERM      # remove on normal exit, Ctrl-C, or SIGTERM

# ... do work inside "$workdir" / write to "$tmpfile" ...
echo "scratch in $workdir"
```

Why `mktemp` rather than `/tmp/myjob.$$`:

- **Race / symlink attacks.** A predictable name in world-writable `/tmp` lets an attacker pre-create a symlink (`/tmp/myjob.1234` → `/etc/passwd`) so your redirect clobbers a sensitive file (a classic *TOCTOU* vulnerability). `mktemp` creates the file **atomically** with `O_CREAT|O_EXCL` and a random suffix, so it fails if the name exists.
- **Permissions.** `mktemp` makes files mode `600` and dirs `700` by default — no world-readable scratch data.
- **Collisions.** The `XXXXXX` template guarantees uniqueness across concurrent runs, unlike `$$` which can recur after PID wraparound.

The `trap ... EXIT INT TERM` is what makes cleanup robust: it fires on the normal path *and* on interruption, so you don't leave scratch directories behind when a job is killed.

#### Q60. [Theory] Explain hardlink count, `unlink`, and exactly when disk space is reclaimed.

Every inode carries a **link count** = the number of hard links (directory entries) pointing to it, plus the kernel separately tracks **open file descriptors** referencing it. The data blocks are freed only when **both** reach zero:

```
space freed  ⇔  (hard-link count == 0)  AND  (open fd count == 0)
```

- `rm` / `unlink(2)` removes *one name* and decrements the link count. If other hard links remain, the data stays.
- If the link count hits 0 but a process still has the file **open**, the data persists (invisible to `ls`, no name) until that process closes the fd or exits. This is the famous "deleted but disk still full" situation.

```bash
stat -c '%h' file                # current hard-link count
ln file file2; stat -c '%h' file # now 2
lsof +L1                         # files with link count < 1 still held open
ls -l /proc/<pid>/fd/            # see the unlinked file still referenced
```

This is *also* a useful idiom, not just a gotcha: programs deliberately `open` then `unlink` a temp file so it's automatically reclaimed when the process dies (no cleanup code needed), and you can recover a wrongly-deleted log that a process still has open by reading `/proc/<pid>/fd/N`.

#### Q61. [Theory] Explain the difference between a process and a thread on Linux, and what `clone()` has to do with it.

On Linux there is really only one primitive — a **task** (`struct task_struct`) — and both processes and threads are created by the same `clone(2)` syscall, differing only in *what they share*. `fork()` is a thin wrapper over `clone()` with almost nothing shared; thread creation (`pthread_create`) calls `clone()` with flags that share the address space and more.

| Shared resource        | Process (`fork`) | Thread (`clone` w/ flags) |
|------------------------|------------------|---------------------------|
| Address space (memory) | **No** (COW copy)| **Yes** (`CLONE_VM`)      |
| File descriptor table  | No (copy)        | **Yes** (`CLONE_FILES`)   |
| Signal handlers        | No               | **Yes** (`CLONE_SIGHAND`) |
| PID (thread group)     | New PID          | Same TGID, distinct TID   |

```bash
ps -eLf                # one row per THREAD (LWP column = thread id)
cat /proc/<pid>/status | grep Threads
ls /proc/<pid>/task/   # one subdir per thread (each is a "task")
```

So a "process" is really a **thread group** (TGID = the PID you see); each thread is a task with its own TID but a shared address space, fds, and signal disposition. This is why `getpid()` returns the same value from every thread, why `top -H` / `ps -eLf` show per-thread CPU, and why the JVM's threads all share the heap but each have their own stack.

#### Q62. [Theory] How does a pipe work internally, and why can a pipeline deadlock or apply backpressure?

A pipe is a fixed-size in-kernel **ring buffer** (64 KiB by default on Linux) with two ends: the write end and the read end, each a file descriptor. The shell creates it with `pipe(2)`, then `fork`s the two stages and `dup2`s the buffer to the children's stdout/stdin.

Flow control is automatic and is the source of both **backpressure** and **deadlock**:

- If the writer outruns the reader and the buffer fills, `write(2)` **blocks** until the reader drains it — natural backpressure that keeps a fast producer from exhausting memory.
- If the reader's buffer is empty, `read(2)` **blocks** until data arrives.
- When all write ends are closed, the reader gets EOF (a 0-length read). When all read ends close, a writer gets **SIGPIPE** (default: terminate) — which is exactly why `cmd | head` makes `cmd` die after `head` exits.

```bash
ulimit -p             # pipe size in 512-byte units (often 8 → 4KiB historically)
cat /proc/sys/fs/pipe-max-size   # max settable pipe capacity
yes | head -1         # 'yes' gets SIGPIPE once head closes the read end
```

Deadlock arises in *bidirectional* setups: if process A writes to B and reads B's output through two pipes, and both fill their buffers waiting for the other to read, neither makes progress — the textbook reason you should not hand-roll two-way pipe communication (use a library, `expect`, or `socat`).

#### Q63. [Practical] What is a zombie process versus an orphan, and how do you actually deal with each?

These are two *normal* states in the process lifecycle, often confused:

- A **zombie** (`Z` / "defunct") is a process that has **exited** but whose parent hasn't `wait()`ed for it yet. It holds no memory or fds — only a tiny entry in the process table keeping its exit status. Harmless in small numbers; dangerous only if a buggy parent never reaps, leaking PT entries until the table fills.
- An **orphan** is a *running* process whose parent **died first**. The kernel immediately **reparents** it to PID 1 (init/systemd), which periodically reaps it. Orphans are not a problem — they're how `nohup`/daemons survive.

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'   # list zombies
ps -el | grep ' Z '
```

How to handle zombies: you **cannot** `kill -9` a zombie (it's already dead). The fix is to make the **parent reap** it — send the parent `SIGCHLD`, or if the parent is broken, kill the parent so its zombies get reparented to PID 1 and reaped. In containers, a common bug is running an app as PID 1 that doesn't reap children, so zombies accumulate — the fix is a tiny init like `tini` or `--init` as PID 1.

#### Q64. [Theory] Explain virtual memory: the difference between VSZ, RSS, PSS, and why a 2 GB JVM can show 8 GB VSZ.

Linux gives every process a private **virtual address space** mapped to physical pages on demand. The metrics measure different slices:

- **VSZ (virtual size)** — the total *address space reserved*, including memory that's mapped but never touched (e.g. the JVM reserving the whole heap up front), shared libraries, and `mmap`'d files. Large and mostly meaningless on its own.
- **RSS (resident set size)** — physical RAM *currently* backing the process, including pages shared with other processes (so summing RSS across processes double-counts shared libs).
- **PSS (proportional set size)** — like RSS but each shared page is divided by the number of sharers, so PSS sums correctly across processes. The honest number for "how much is this process really costing."
- **USS (unique set size)** — pages private to this process; what you'd reclaim by killing it.

```bash
ps -o pid,vsz,rss,comm -p <pid>
cat /proc/<pid>/smaps_rollup        # Rss, Pss, Private/Shared clean/dirty
grep -E '^(Rss|Pss):' /proc/<pid>/smaps | awk '{s+=$2} END{print s}'
```

So an 8 GB VSZ on a `-Xmx2g` JVM is normal: it includes the *reserved* (not committed) heap, thread stacks (~1 MB each × hundreds of threads), the code cache, mapped jars, and glibc arenas. Alert on **RSS/PSS**, not VSZ — VSZ rarely correlates with real memory pressure.

#### Q65. [Coding] Write an `awk` program that computes the average and p95 of response times in column 7 of a log. Explain the approach.

```bash
awk '
{
    t = $7 + 0            # coerce field 7 to a number
    sum += t
    n++
    times[n] = t          # store every value for percentile
}
END {
    if (n == 0) { print "no data"; exit 1 }
    # sort the values ascending (insertion sort; fine for moderate n)
    for (i = 2; i <= n; i++) {
        v = times[i]; j = i - 1
        while (j >= 1 && times[j] > v) { times[j+1] = times[j]; j-- }
        times[j+1] = v
    }
    idx = int(0.95 * n + 0.5)      # nearest-rank p95
    if (idx < 1) idx = 1
    printf "count=%d  avg=%.2f  p95=%.2f\n", n, sum/n, times[idx]
}
' access.log
```

The approach: a streaming pass accumulates the running `sum`/`count` for the mean and buffers all values into an associative array. In the `END` block we sort the buffered values and pick the **nearest-rank** element for p95 (`ceil(0.95 × n)`). Key `awk` details: `$7 + 0` forces numeric context (fields are strings by default); `times[n]` uses awk's associative arrays as a dynamic array; and everything runs in one process with no external `sort`/`tail`. For very large inputs where buffering all values is too costly, you'd switch to a streaming quantile estimator (t-digest) — worth mentioning as the scale-out answer.

#### Q66. [Theory] Explain the dynamic linker: what happens between `execve` and `main()`, and what `ldd`, `LD_LIBRARY_PATH`, and `LD_PRELOAD` do.

When you `execve` a dynamically-linked ELF binary, the kernel loads it and, seeing a `PT_INTERP` header, also loads the **dynamic linker/loader** (`ld-linux-x86-64.so.2`) and transfers control to *it* — not to `main()` yet. The loader then:

1. Reads the binary's `DT_NEEDED` entries (the shared libraries it requires, e.g. `libc.so.6`).
2. **Searches** for each: `DT_RPATH`/`DT_RUNPATH`, then `LD_LIBRARY_PATH`, then the cache `/etc/ld.so.cache` (built by `ldconfig` from `/etc/ld.so.conf`), then default `/lib`, `/usr/lib`.
3. `mmap`s the libraries and performs **relocations**, resolving symbols. By default this is **lazy** (PLT/GOT) — a function is resolved on first call — unless `LD_BIND_NOW`/`RELRO` forces it eager.
4. Runs initializers, then jumps to the program's entry point → eventually `main()`.

```bash
ldd /usr/bin/curl              # which shared libs it resolves (and to where)
ldd /usr/bin/curl | grep 'not found'   # missing-dependency diagnosis
LD_LIBRARY_PATH=/opt/lib ./app # prepend a search dir (testing/dev)
LD_PRELOAD=./mymalloc.so ./app # force-load a lib FIRST → override symbols
ldconfig -p | grep ssl         # what's in the loader cache
```

`LD_PRELOAD` is the powerful/dangerous one: the preloaded library's symbols win over later ones, so you can intercept `malloc`, `open`, etc. — used legitimately for profilers (jemalloc), sandboxing, and fault injection, and maliciously for rootkits (which is why it's ignored for setuid binaries). Statically-linked or musl binaries skip most of this dance.

#### Q67. [Theory] What does `ulimit` control, where do the limits actually live, and how do soft vs. hard limits differ?

`ulimit` is the shell front-end to `setrlimit(2)` — per-process **resource limits** the kernel enforces, inherited by children. Each limit has a **soft** value (the currently enforced ceiling) and a **hard** value (the maximum the soft can be raised to; only root can raise the hard limit).

```bash
ulimit -a              # show all current limits
ulimit -n              # soft limit on open file descriptors (the famous one)
ulimit -Hn             # hard limit on fds
ulimit -n 65536        # raise the SOFT fd limit (up to the hard cap)
ulimit -u              # max user processes (guards against fork bombs)
ulimit -c unlimited    # enable core dumps
cat /proc/<pid>/limits # the limits actually in force for a RUNNING process
```

The interview-classic failure is **"Too many open files"** (`EMFILE`): a server hitting its `RLIMIT_NOFILE`. Raising it in the shell only affects that shell's children, so for a service you set it in the **systemd unit** (`LimitNOFILE=65536`) — *not* `/etc/security/limits.conf`, which is read by PAM for login sessions and is ignored for systemd-managed services. Always verify with `/proc/<pid>/limits`, because the value the daemon actually got is frequently not the one you edited.

#### Q68. [Practical] Compare `>`, `>>`, `2>&1`, `&>`, and `<<<`/`<<` here-strings/here-docs, with the exact descriptor mechanics.

Each operator manipulates file descriptors via `dup2`/`open` before the command runs:

```bash
cmd > file       # open file (truncate), dup2 it onto fd 1
cmd >> file      # open file (O_APPEND), dup2 onto fd 1 — atomic appends
cmd 2> file      # same, onto fd 2 (stderr)
cmd > f 2>&1     # fd1→file, THEN fd2 = copy of fd1 (both to file). Order matters.
cmd 2>&1 > f     # fd2 = copy of current fd1 (terminal!), THEN fd1→file. Classic bug.
cmd &> file      # bash shortcut: BOTH fd1 and fd2 → file
cmd &>> file     # both, appending
cmd 2>&1 1>&3    # advanced: swap streams using a saved fd 3
```

Here-documents and here-strings feed **stdin** from inline text instead of a file:

```bash
cat <<'EOF'      # here-doc: quoted EOF = NO expansion of $vars
literal $HOME
EOF

cat <<-EOF       # the - strips leading TABS (for indented heredocs)
	indented with tabs, stripped
EOF

grep foo <<< "$myvar"   # here-string: feed a single string to stdin
```

The mechanism to articulate: `2>&1` means "make fd 2 a *duplicate of wherever fd 1 points right now*." Because redirections are applied **left to right**, the order flips the meaning entirely — `> f 2>&1` sends both to the file, while `2>&1 > f` sends stderr to the original terminal and only stdout to the file. A quoted heredoc delimiter (`'EOF'`) disables variable/command expansion in the body; an unquoted one expands it.

#### Q69. [Theory] Explain the Linux CFS scheduler (and EEVDF) — how does the kernel decide which runnable task runs next?

For most of the last decade the default scheduler for normal tasks was **CFS (Completely Fair Scheduler)**; since kernel 6.6 (2023) it has been replaced by **EEVDF (Earliest Eligible Virtual Deadline First)**, the model you should reference in 2026. Both pursue *fairness* rather than fixed priorities:

- **CFS** tracked each task's **`vruntime`** (virtual runtime, weighted by niceness) and always ran the task with the *smallest* vruntime, using a red-black tree keyed on vruntime. A "nicer" task accrues vruntime faster, so it's scheduled less. There were no fixed timeslices; the period was divided proportionally.
- **EEVDF** refines this with a **virtual deadline** per task derived from its requested "slice" (latency) and its lag (how much CPU it's owed). It runs the *eligible* task with the earliest virtual deadline, which gives latency-sensitive tasks better responsiveness without abandoning fairness. Niceness now maps more directly to both the share of CPU and the latency target.

```bash
chrt -p <pid>              # show scheduling policy & RT priority
nproc                      # logical CPUs the scheduler balances across
cat /proc/<pid>/sched      # per-task scheduler stats (vruntime-era fields)
cat /sys/kernel/debug/sched/latency_ns   # tunables (debugfs)
```

Above this sit **real-time** policies (`SCHED_FIFO`, `SCHED_RR`, set with `chrt`) that *always* preempt normal tasks — used for audio/control loops, dangerous because a busy RT task can starve everything. `SCHED_IDLE` is the opposite (run only when nothing else wants the CPU). The practical takeaway: niceness biases the *fair share*; for hard guarantees you need RT policies or cgroup `cpu.max` quotas, not nice.

#### Q70. [Theory] Explain swap and the role of `vm.swappiness`. Why can a box with free RAM still swap, and why is swap not simply "bad"?

**Swap** is disk space the kernel uses to evict **anonymous** pages (heap/stack — pages not backed by a file) when it wants to reclaim RAM. File-backed pages don't need swap; they're just dropped (and re-read from disk later). Swapping lets the system survive transient memory spikes and lets the kernel evict *cold* anonymous pages to make room for hot page cache.

`vm.swappiness` (0–200, default 60) is the kernel's **preference for reclaiming anonymous pages (swapping) vs. dropping file-cache pages**. Low swappiness → prefer evicting page cache and keep anon in RAM; high → more willing to swap anon out.

```bash
cat /proc/sys/vm/swappiness          # default 60
sysctl -w vm.swappiness=10           # bias toward keeping app memory resident
swapon --show                        # active swap devices/files and usage
free -h                              # Swap row: total/used/free
vmstat 1                             # si/so columns = swap-in/swap-out per sec
```

Why a box with "free" RAM still swaps: with default swappiness the kernel may **proactively** swap out long-idle anonymous pages to grow the page cache — perfectly fine. The real problem is **thrashing**: under true pressure, hot pages get swapped out and immediately faulted back in (`si`/`so` high in `vmstat`), and latency collapses because every access waits on disk. So the nuance to deliver: a little swap usage is healthy headroom; *sustained high swap I/O* is the pathology. On latency-critical DB/JVM hosts you often set low swappiness (or disable swap and rely on cgroup limits + OOM), while on memory-constrained boxes some swap prevents premature OOM kills.

#### Q71. [Practical] Explain `mmap` vs `read`/`write` I/O, and when memory-mapped files help or hurt.

There are two ways to access a file's bytes:

- **`read`/`write`** copy data between the kernel's page cache and a userspace buffer via syscalls. Each call is a syscall + a copy.
- **`mmap`** maps the file's pages directly into the process's address space; accessing the memory faults the pages in from the page cache **without a copy or a per-access syscall**. Writes go to the dirty pages and are flushed by the kernel (or `msync`).

```bash
strace -e trace=mmap,read,write ./app   # see which strategy a program uses
pmap -x <pid> | grep -i '\.dat'         # file-backed mappings in the address space
cat /proc/<pid>/smaps | grep -A1 myfile # per-mapping Rss/Pss for the mapped file
```

When `mmap` **wins**: random access over a large file (databases like SQLite/LMDB, and the JVM's mapped `ByteBuffer`s) — no syscall per access, the OS page cache does the caching, and pages are shared across processes mapping the same file. When it **hurts**: sequential streaming (plain `read` with readahead is often as fast and simpler), small files (mapping overhead dominates), and *latency surprises* — a touch of an unmapped page is a blocking **major page fault** that can stall a thread on disk I/O at an unpredictable moment (a real problem for low-latency JVM apps using mapped files). Also, I/O errors surface as **SIGBUS** on access rather than a clean error return from `read`, which is harder to handle. This is exactly why "off-heap" mapped buffers can cause mysterious latency spikes that don't show up as heap pressure.

#### Q72. [Coding] Write a Bash script that uses a `flock`-based lock to ensure only one instance runs at a time, and explain the kernel mechanism.

```bash
#!/usr/bin/env bash
set -euo pipefail

LOCKFILE="/var/lock/myjob.lock"

# Open the lock file on fd 9 for the lifetime of the script
exec 9>"$LOCKFILE"

# Non-blocking exclusive lock; bail out if another instance holds it
if ! flock -n 9; then
    echo "another instance is already running; exiting" >&2
    exit 1
fi

# --- critical section: guaranteed single-instance ---
echo "running with the lock (pid $$)"
sleep 5
# Lock is released automatically when fd 9 closes (script exit) — no cleanup race
```

The mechanism: `flock(2)` places an **advisory** lock on the *open file description* (not the path). `exec 9>file` opens the file once and keeps the descriptor for the whole script; `flock -n 9` takes a non-blocking exclusive (`LOCK_EX`) lock on it. Because the lock is tied to the open file description, it is **released automatically when the process exits** (even on `kill -9` or a crash) — there is no stale-lock cleanup problem like with naive "create a PID file" schemes, where a crash leaves the file behind. "Advisory" means only cooperating processes that also `flock` are blocked; it doesn't stop an unrelated process from writing the file. Use `flock` for cron jobs that must not overlap (`flock -n /var/lock/x -c 'job'` is the one-liner form). For NFS, advisory `flock` semantics are unreliable — prefer `lockf`/`fcntl` or a coordination service.

#### Q73. [Theory] Explain how `sudo` works under the hood — setuid, `/etc/sudoers`, PAM, and what makes it more secure than a root shell.

`sudo` is a **setuid-root** binary: when an ordinary user runs it, the kernel executes it with the file owner's (root's) effective UID, so it *starts* with root privileges. From there sudo does the security work itself:

1. **Authentication via PAM** — it consults the PAM stack (`/etc/pam.d/sudo`), typically prompting for *your* password (cached briefly per-tty), and can chain MFA, LDAP, etc.
2. **Authorization via `/etc/sudoers`** — parsed by `visudo` (which syntax-checks before saving). Rules specify *which users* may run *which commands* *as which target users* on *which hosts*, e.g. `alice ALL=(root) /usr/bin/systemctl restart myapp`.
3. **Privilege transition** — it sets the requested UID/GID, sanitizes the environment (`env_reset`, `secure_path`), and `execve`s the target command.
4. **Auditing** — every invocation is logged (who ran what, when) to the journal/`/var/log`.

```bash
sudo -l                        # what am I allowed to run?
sudo -u deploy -- whoami       # run as a specific non-root user
visudo                         # the ONLY safe way to edit sudoers (validates)
sudo -k                        # forget the cached credential timestamp
```

Why it beats `su -`/a root shell: **least privilege + accountability**. Instead of handing out the root password and an unrestricted shell, sudo grants *specific commands* to *named users*, logs every action to the audit trail, and resets the environment to prevent `LD_PRELOAD`/`PATH` injection. The risk surface is the sudoers policy itself — overly broad rules (`ALL`), or allowing a command that can spawn a shell (`vim`, `less`, `find -exec`) re-open a full root shell (`sudo less` → `!sh`), defeating the restriction (the GTFOBins problem).

#### Q74. [Practical] How do you measure and reason about per-process I/O, and what does the `D` (uninterruptible sleep) state really mean?

The `D` state is **uninterruptible sleep** — a task blocked in the kernel waiting on something (almost always disk or network-filesystem I/O) that *cannot be interrupted by signals*, which is exactly why you can't `kill -9` a process stuck in `D` (the kernel won't deliver the signal until the I/O completes). A pile of `D`-state tasks is the signature of a **saturated or hung storage layer** (slow disk, stuck NFS mount), and because load average counts `D` tasks, it inflates load even with idle CPUs.

```bash
ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /D/'   # who is in D and where (wchan)
iostat -xz 1                # %util ~100 and high await = disk saturated
iotop -oP                   # per-process read/write rates (needs root)
pidstat -d 1                # per-process disk I/O (kB read/write per sec)
cat /proc/<pid>/io          # cumulative bytes read/written by THIS process
cat /proc/<pid>/stack       # kernel stack: WHAT it's blocked in (if accessible)
```

Reasoning workflow: high load + low `%us`/`%sy` but high `%wa` (or many `D` tasks) ⇒ I/O bound, not CPU bound. `iostat -x` tells you *which device* is saturated (`%util`, `await`); `iotop`/`pidstat -d` tells you *which process* is driving it; `/proc/<pid>/stack` or `wchan` tells you *what kernel function* it's stuck in (e.g. `nfs_*` for a hung NFS server). The trap is "throw CPU at it" — adding cores does nothing when every thread is parked in `D` waiting on a slow disk.

#### Q75. [Theory] Explain TCP connection state, `TIME_WAIT` accumulation, and the socket-level tunables that matter under load.

A TCP socket walks a state machine; the states that bite under load are the ones a server accumulates:

- **`TIME_WAIT`** — the side that closes *actively* (sends the final ACK) holds the socket for ~2×MSL (often 60s) so late/duplicate packets can't corrupt a new connection on the same 4-tuple. A high-throughput client or a proxy that opens/closes many short connections can pile up tens of thousands of `TIME_WAIT` sockets, exhausting **ephemeral ports** (`net.ipv4.ip_local_port_range`).
- **`CLOSE_WAIT`** — the *peer* closed but the local app hasn't called `close()`. Growing `CLOSE_WAIT` is an **application bug** (leaked sockets / not closing connections), not a kernel-tuning issue.

```bash
ss -tan state time-wait | wc -l        # how many TIME_WAIT sockets
ss -s                                  # summary by state
ss -tan state close-wait               # CLOSE_WAIT — suspect the app
sysctl net.ipv4.ip_local_port_range    # ephemeral port pool size
sysctl net.ipv4.tcp_tw_reuse           # safely reuse TW sockets for new outbound conns
sysctl net.core.somaxconn              # max accept-queue backlog
sysctl net.ipv4.tcp_max_syn_backlog    # half-open (SYN) queue size
```

What to tune and what *not* to: for an outbound-heavy client drowning in `TIME_WAIT`, enable `net.ipv4.tcp_tw_reuse=1` (safe for outbound connections; uses timestamps to avoid collisions) and widen the ephemeral range — but **never** the old `tcp_tw_recycle` (removed; it broke NAT). For an accept-heavy server seeing dropped connections under burst, raise `somaxconn` *and* the app's `listen()` backlog together (both gate the queue). And `CLOSE_WAIT` growth always points back to code that forgot to close sockets — no sysctl fixes a descriptor leak.

#### Q76. [Theory] Explain how strace works (ptrace), why it's so expensive, and what eBPF changes about production tracing.

`strace` is built on **`ptrace(2)`**: it attaches to the target as a "tracer," and the kernel **stops the tracee on every syscall entry and exit**, hands control to strace to read the registers/arguments (and follow pointers into the tracee's memory), then resumes it. That means *two* context switches into the tracer **per syscall** plus memory peeks — so a syscall-heavy process can run **10–100× slower** under strace. This is why attaching strace to a hot production service is dangerous: you can tip a struggling process into timeouts or change its timing enough to mask the bug (a Heisenbug).

```bash
strace -c -p <pid>          # SUMMARY mode: counts/time per syscall, least intrusive
strace -f -e trace=%file ./app   # syscall groups (file, network, process, signal)
strace -p <pid> -T -tt      # per-syscall duration + wallclock timestamp
```

**eBPF** changes the game for production. Instead of stopping the process on every syscall, eBPF lets you attach a tiny **verified, JIT-compiled program inside the kernel** to tracepoints/kprobes/uprobes/USDT that aggregates in-kernel and only ships summaries to userspace — observability with **near-zero overhead and no process stops**:

```bash
# bpftrace one-liners — safe on production
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
opensnoop-bpfcc             # which files are being opened, system-wide
biolatency-bpfcc            # block I/O latency as a histogram
execsnoop-bpfcc             # every process exec, live
funclatency-bpfcc           # latency distribution of a function
```

The 2026 rule of thumb: reach for `strace -c` for a quick one-off on a non-critical process, but for *production* tracing of latency, I/O, and syscalls, use **eBPF (bpftrace/bcc/perf)** — it's the difference between halting the patient to examine it and watching them on a low-overhead monitor.

#### Q77. [Theory] Explain copy-on-write `fork`, why a large-heap JVM can fail to fork a child, and how `posix_spawn`/`vfork` and overcommit relate.

`fork()` is cheap because of **copy-on-write (COW)**: the child gets a *logical* duplicate of the parent's address space, but the kernel doesn't copy pages — it marks them read-only and shared, copying a page only when either side **writes** to it. So forking a process with a 30 GB heap doesn't immediately use 60 GB; pages are duplicated lazily on write.

The classic failure is **fork() ENOMEM on a big-heap process running an external command**: even with COW, the kernel must account for the *possibility* that the child writes every shared page, so under **strict overcommit** (`vm.overcommit_memory=2`) it requires enough commit charge (RAM+swap) to back a full copy of the parent — a 30 GB JVM that shells out to run `ls` can get `Cannot allocate memory` even though the child instantly `exec`s and touches almost nothing.

```bash
cat /proc/sys/vm/overcommit_memory     # 0 heuristic, 1 always, 2 strict accounting
cat /proc/sys/vm/overcommit_ratio
grep -i commit /proc/meminfo           # CommitLimit vs Committed_AS
```

Mitigations and relatives:

- **`posix_spawn`/`vfork`** — `vfork` (and `posix_spawn` built on it) **don't COW-duplicate** the address space; the child borrows the parent's memory and must immediately `exec`, so there's no commit charge for a full copy. Modern runtimes (and the JVM's `Runtime.exec` on Linux via `posix_spawn`) use this to avoid the fork-bomb-the-heap problem.
- **Overcommit tuning** — heuristic overcommit (`0`, the default) usually permits the fork; strict accounting (`2`) is safer for predictability but is exactly what makes big-heap forks fail.
- **The JVM-specific fix** — historically people set `vfork`/`posix_spawn` launch mechanisms or kept a small "launcher" process to spawn children, so a multi-GB heap never has to be (notionally) duplicated.

#### Q78. [Practical] You see intermittent latency spikes on a JVM service with no GC correlation. Walk through a kernel-level investigation.

When app-level (GC logs, profiler) shows nothing, the cause is usually *below* the JVM. Investigate the stalls the application can't see:

```bash
# 1. Transparent Huge Pages — a notorious source of multi-ms stalls (khugepaged compaction)
cat /sys/kernel/mm/transparent_hugepage/enabled    # [always] madvise never
grep -i 'thp\|compact' /proc/vmstat                # compaction stalls

# 2. Page faults / reclaim — major faults block the thread on disk
pidstat -r -p <pid> 1      # majflt/s — major faults = blocking disk reads
sar -B 1                   # pgscan/pgsteal = reclaim pressure

# 3. CPU scheduling latency / steal / throttling
mpstat -P ALL 1            # %steal (noisy-neighbor on a hypervisor)
cat /sys/fs/cgroup/<svc>/cpu.stat   # nr_throttled / throttled_usec → cgroup CPU throttling!

# 4. NUMA effects — remote-memory access penalty
numactl --hardware         # node layout
numastat -p <pid>          # local vs remote allocations

# 5. eBPF for the actual stall
bpftrace -e 'tracepoint:sched:sched_switch /args->prev_comm=="java"/ { @=count(); }'
runqlat-bpfcc              # run-queue latency: time runnable-but-not-running
```

The likeliest culprits to name, in order: **cgroup CPU throttling** — a container with `CPUQuota`/`cpu.max` that exhausts its quota gets *parked* until the next period (visible as `nr_throttled` in `cpu.stat`), causing periodic multi-ms freezes uncorrelated with GC; **THP compaction** stalls (recommend `madvise` or `never` for latency-sensitive JVMs); **major page faults** from mapped files or swapped pages; **`%steal`** from a noisy hypervisor neighbor; and **NUMA** remote-memory penalties when the JVM's threads and heap land on different nodes. The meta-point: GC is only one stall source — `runqlat`/`cpu.stat`/`majflt` reveal the stalls that never appear in a JVM profiler.

#### Q79. [Theory] Explain the Linux boot sequence from power-on to a login prompt, including the initramfs and systemd targets.

The chain hands control through progressively higher-level stages:

```
firmware (UEFI/BIOS) → bootloader (GRUB) → kernel + initramfs → systemd (PID 1) → targets → login
```

1. **Firmware (UEFI/BIOS)** runs POST, then reads the **EFI System Partition** and loads the boot manager (UEFI) or runs MBR boot code (legacy BIOS).
2. **Bootloader (GRUB2)** presents the menu, loads the selected **kernel** (`vmlinuz`) and the **initramfs** into memory, and passes the kernel command line (`root=`, etc.).
3. **Kernel** decompresses, initializes memory management/scheduler/drivers, and mounts the **initramfs** as a temporary root.
4. **initramfs** is a small in-memory filesystem holding *just enough* drivers/tools (e.g. LVM, LUKS decryption, RAID, network for iSCSI) to **find and mount the real root filesystem** — solving the chicken-and-egg problem where the driver to read the root disk lives *on* the root disk. It then `switch_root`s to the real `/`.
5. **systemd (PID 1)** takes over, reads units, and activates the default **target** (a named group of units replacing old runlevels): `basic.target` → `multi-user.target` (networked, no GUI) → optionally `graphical.target`.
6. **getty/display manager** presents the login prompt; PAM authenticates.

```bash
systemd-analyze                 # total boot time
systemd-analyze blame           # slowest units (boot-time tuning)
systemd-analyze critical-chain  # the critical path through the dependency tree
systemctl get-default           # the default target (multi-user vs graphical)
journalctl -b                   # this boot's log; -b -1 = previous boot
lsinitrd /boot/initramfs-*.img  # inspect what's inside the initramfs (RHEL)
```

The two deep points: the **initramfs exists to bootstrap access to the real root** (decrypt LUKS, assemble LVM/RAID, load storage drivers) before the real filesystem is available; and systemd **targets are dependency-resolved unit groups**, not sequential runlevels — `systemd-analyze critical-chain` shows the real parallelized boot path, which is how you diagnose a slow boot.

#### Q80. [Theory] Explain journald's binary journal vs. classic syslog/rsyslog — storage, structure, and the trade-offs.

`systemd-journald` collects logs into a **structured, indexed binary** format, a departure from the plaintext line-per-event model of syslog:

- **Structure.** Each entry is a set of **key=value fields** (`_PID`, `_SYSTEMD_UNIT`, `_UID`, `PRIORITY`, `MESSAGE`, `_BOOT_ID`, plus trusted fields the kernel/journald stamp that *can't be forged* by the logging process). This lets you query by field rather than grep text: `journalctl _SYSTEMD_UNIT=myapp.service PRIORITY=3`.
- **Storage.** Binary files in `/var/log/journal` (persistent) or `/run/log/journal` (volatile, RAM, lost on reboot — the default until you `mkdir /var/log/journal`). Files are indexed for fast time/field seeks and support **forward secure sealing (FSS)** to detect tampering.
- **Integration.** Captures everything — stdout/stderr of services, kernel ring buffer, early-boot messages — with per-unit attribution automatically, no app-side syslog config.

```bash
journalctl -u myapp -o json-pretty       # see ALL structured fields of each entry
journalctl --disk-usage                  # journal size on disk
journalctl --vacuum-size=500M            # trim; or --vacuum-time=2weeks
journalctl _COMM=sshd _PID=1234          # field-based filtering
journalctl -f -o cat | logger            # forward to syslog if needed
```

Trade-offs to articulate: the journal gives you **rich, queryable, attributed, tamper-evident** logs and unified collection — but it's **binary** (you need `journalctl`, not `tail`/`grep`), can be lost on reboot if not made persistent, and isn't a network log shipper. So the common production pattern is **both**: journald locally for rich structured queries, *forwarded* to `rsyslog`/`syslog-ng` or a pipeline (Vector/Fluent Bit → Loki/Elasticsearch) for central, long-term, cross-host aggregation. Classic `rsyslog` still wins where you need plaintext files, RFC5424 network forwarding, or integration with tools that expect `/var/log/*.log`.

#### Q81. [Theory] Explain how Linux capabilities decompose root, and why `CAP_NET_BIND_SERVICE` or dropping `CAP_SYS_ADMIN` matters.

Historically root (UID 0) was **all-or-nothing**. **Capabilities** split the monolithic root privilege into ~40 independent units, so a process can hold *exactly* the powers it needs and nothing more — the foundation of least-privilege daemons and containers.

| Capability             | Grants                                                        |
|------------------------|--------------------------------------------------------------|
| `CAP_NET_BIND_SERVICE` | bind to privileged ports < 1024 (e.g. 80/443) without root   |
| `CAP_NET_RAW`          | raw sockets (what `ping`/`tcpdump` need)                     |
| `CAP_SYS_ADMIN`        | a huge grab-bag (mount, many admin ops) — "the new root"    |
| `CAP_DAC_OVERRIDE`     | bypass file permission checks                                |
| `CAP_SYS_PTRACE`       | trace/`ptrace` other processes                               |
| `CAP_CHOWN`            | change file ownership                                        |

```bash
getcap /usr/bin/ping                 # cap_net_raw set on the binary (no setuid!)
setcap 'cap_net_bind_service=+ep' /usr/bin/myserver   # let it bind :443 as non-root
cat /proc/<pid>/status | grep -i cap # CapEff/CapPrm/CapBnd bitmasks in effect
capsh --decode=00000000a80425fb      # decode a capability bitmask
```

Why it matters concretely: instead of running Nginx as root just to bind port 80, grant the binary `CAP_NET_BIND_SERVICE` (or use systemd `AmbientCapabilities=CAP_NET_BIND_SERVICE`) and run it as an **unprivileged user** — drastically shrinking the blast radius if it's compromised. Containers/systemd go further by **dropping** capabilities (`CapabilityBoundingSet`, Docker `--cap-drop=ALL --cap-add=...`): a web app almost never needs `CAP_SYS_ADMIN`, so dropping it neuters whole classes of escapes. The one to fear is `CAP_SYS_ADMIN` — it's so broad (mounts, namespaces, many ioctls) that holding it is nearly equivalent to root, so granting it defeats the purpose of capabilities.

#### Q82. [Practical] A binary works when run by hand but fails under systemd. Enumerate the systemd sandboxing/environment differences that explain this.

This is a very common "works in my shell, fails as a service" puzzle, and almost always it's the *differences in the systemd execution environment*, not the binary:

```bash
systemctl cat myapp.service          # see the actual unit, drop-ins included
systemctl show myapp.service         # ALL effective properties (env, limits, sandbox)
systemd-analyze security myapp.service   # score & list active hardening options
journalctl -u myapp -b               # the real error (often a permission/path failure)
systemd-run -p <prop>=... /the/binary  # reproduce under systemd's environment to bisect
```

The usual suspects, each of which differs from an interactive shell:

- **Minimal environment.** systemd does *not* source `~/.bashrc`/`/etc/profile`. Your `PATH` is short, `JAVA_HOME`/custom vars are unset, locale differs. Fix with `Environment=`/`EnvironmentFile=`.
- **Working directory.** Defaults to `/`, not where you ran it — relative paths break. Set `WorkingDirectory=`.
- **Different user / no TTY.** Runs as `User=` (often a service account) with no controlling terminal and no login session — `$HOME` may be `/` or unset, `sudo` prompts hang, and anything expecting a TTY fails.
- **Sandboxing directives (the big one in 2026).** Hardening options silently block things: `ProtectSystem=strict`/`ReadOnlyPaths=` make the FS read-only (writes get `EROFS`), `PrivateTmp=yes` gives a *private* `/tmp` (so files it expects in the shared `/tmp` aren't there), `ProtectHome=`, `PrivateNetwork=`, `RestrictAddressFamilies=`, `MemoryDenyWriteExecute=` (breaks JITs), `SystemCallFilter=` (seccomp — blocks syscalls), `NoNewPrivileges=` (defeats setuid/capabilities), `CapabilityBoundingSet=` (e.g. no `CAP_NET_BIND_SERVICE` → can't bind :80).
- **Resource limits.** `LimitNOFILE=`/`MemoryMax=`/`TasksMax=` differ from your shell's `ulimit`, so the service hits `EMFILE`/OOM the shell never would.

The systematic approach: `systemctl show` to see the *effective* config, `systemd-analyze security` to spot active sandboxing, then reproduce with `systemd-run` to bisect which directive breaks it — far faster than guessing.

#### Q84. [Practical] A teammate ran `chmod -R 777 /opt/app` "to fix a permission error" and now the service won't start. How do you reason about and repair it?

`777` made every file and directory world-writable *and* world-executable, which is both a security finding and, paradoxically, often the cause of a *new* failure: many daemons (`sshd`, `postfix`, and security tooling) **refuse to use** config files, key files, or directories that are group/world-writable. So "fix the permissions" actually broke startup.

Repair by restoring sane, least-privilege defaults rather than guessing per-file:

```bash
# Directories need x (traverse); files generally don't.
find /opt/app -type d -exec chmod 755 {} +     # rwxr-xr-x dirs
find /opt/app -type f -exec chmod 644 {} +     # rw-r--r-- files
# Re-add execute only where it's actually needed
chmod 755 /opt/app/bin/*                        # executables/scripts
chmod 600 /opt/app/conf/*.key                   # secrets owner-only
chown -R appuser:appuser /opt/app               # fix ownership too
```

The reasoning to verbalize: blanket-recursive `chmod` destroys the *distinction* between dirs (need `x`) and files (usually don't), and between secrets (`600`) and code. The split-by-`-type` `find` restores that distinction in two commands. Going forward, the right fix for the *original* error is to identify the one path with wrong ownership/mode (`namei -l /opt/app/conf/app.yml` shows the permission of every component in the path) and correct *that*, never to `777` the tree.

#### Q85. [Coding] Write a one-liner that, given a log file, prints the count of each distinct HTTP status code (field 9 of a combined access log), highest first.

#### Q86. [Practical] `tail -f app.log` shows nothing new even though the app is clearly serving traffic. What are the likely causes and how do you confirm?

Several distinct culprits produce "the log went quiet":

1. **Log rotation happened.** `tail -f` follows the *inode*; after `logrotate` renames `app.log` → `app.log.1` and creates a fresh `app.log`, your `tail` is still watching the old (now-renamed) file. Use `tail -F` (capital F = follow by *name*, re-open on rotation).
2. **The app buffers stdout.** When stdout is a pipe/file rather than a TTY, libc uses block buffering, so lines sit in a 4–8 KB buffer until it fills. Confirm with `strace`.
3. **It's logging somewhere else** — journald, a different path, or stderr.

```bash
tail -F app.log                      # survive rotation (re-open by name)
ls -li app.log                       # did the inode change? (rotation)
lsof -p <pid> | grep -i log          # what file is the process ACTUALLY writing?
ls -l /proc/<pid>/fd | grep log      # same, via /proc
strace -f -e trace=write -p <pid>    # is it write()ing at all, and to which fd?
journalctl -u myapp -f               # maybe it's going to the journal
```

The fastest disambiguation: `lsof -p <pid> | grep log` (or `ls -l /proc/<pid>/fd`) tells you the *exact* file the process holds open — if it's `app.log.1`, you've confirmed rotation; if it's a different path entirely, you were tailing the wrong file. For the buffering case, run the app with `stdbuf -oL` (line-buffered) or fix the logging config.

#### Q87. [Coding] Write a script that takes a directory and prints, for each file extension, how many files have it and their total size.

```bash
#!/usr/bin/env bash
set -euo pipefail
dir="${1:?usage: $0 <dir>}"

find "$dir" -type f -printf '%s %f\n' | awk '
{
    n = split($2, parts, ".")
    ext = (n > 1) ? parts[n] : "(none)"
    count[ext]++
    bytes[ext] += $1
}
END {
    for (e in count)
        printf "%-12s files=%-6d bytes=%d\n", e, count[e], bytes[e]
}' | sort -t= -k3 -rn
```

Key choices: `find -printf '%s %f\n'` emits *size and basename* without an extra `stat` per file (much faster than a Bash loop calling `stat`), and it's robust to paths with spaces because we only consume one field for size and the rest as the name. `awk`'s `split` on `.` extracts the extension, with `(none)` for extensionless files. For NUL-safe handling of *truly* pathological names (newlines in filenames), switch to `-printf '%s\t%f\0'` and an `awk`/`while` reader with `RS='\0'`.

#### Q88. [Practical] You need to find every file under `/var` modified in the last 10 minutes (e.g. "what did this deploy touch?"). Show the command and the gotchas.

#### Q90. [Practical] A cron job "didn't run" last night. Walk through how you diagnose a silently failing cron entry.

Cron failures are almost always *environment* problems, because cron runs with a deliberately bare environment, not your interactive shell. Work through it:

```bash
crontab -l                                  # is the entry even there / correctly scheduled?
grep -i cron /var/log/syslog                # Debian/Ubuntu: cron LOGS each run it started
journalctl -u cron -u crond --since yesterday   # systemd distros
# Did the COMMAND fail? Cron mails output to the user — check local mail or redirect:
#   * * * * * /opt/job.sh >> /var/log/job.log 2>&1
```

The four classic root causes, in order of frequency:

1. **`PATH` is minimal** (`/usr/bin:/bin`) — your `java`/`aws`/custom binary isn't found. Fix: use **absolute paths** or set `PATH=` at the top of the crontab.
2. **No profile sourced** — `JAVA_HOME` and other vars from `~/.bashrc` are unset. Set them explicitly in the crontab or the script.
3. **`%` is special in crontab** — an unescaped `%` (e.g. in a `date +%F`) is treated as a newline; escape it `\%`.
4. **The schedule is wrong** — `cron` ran, but not when you thought (timezone, day-of-week 0–7, or DST). Confirm the *intended* minute with a tool like crontab.guru.

The diagnostic that cuts through it: temporarily change the command to `* * * * * env > /tmp/cronenv 2>&1` to capture cron's *actual* environment, then `diff` it against your shell's `env` — the missing `PATH`/var jumps out immediately.

#### Q91. [Coding] Write a script that watches a log file and sends an alert (prints to stderr) the first time a given error pattern appears.

```bash
#!/usr/bin/env bash
set -euo pipefail

logfile="${1:?usage: $0 <logfile> <pattern>}"
pattern="${2:?usage: $0 <logfile> <pattern>}"

# tail -F survives rotation; --line-buffered makes grep emit matches immediately
tail -Fn0 "$logfile" | grep --line-buffered -m1 -e "$pattern" | while IFS= read -r line; do
    printf 'ALERT %s :: matched: %s\n' "$(date '+%F %T')" "$line" >&2
    # hook a real notifier here, e.g. curl to a webhook

done
```

The load-bearing flags: `tail -Fn0` follows by *name* (survives rotation) and starts at the *end* (`-n0`, so old matches don't fire); `grep --line-buffered` forces grep to flush each match instead of block-buffering (otherwise the alert is delayed until grep's buffer fills); and `-m1` makes grep exit after the first match for a one-shot alert. #### Q92. [Practical] How do you check whether a specific port is open and *which process* owns it, and what do you do when it says "Address already in use"?

```bash
ss -tlnp '( sport = :8080 )'        # who's LISTENING on 8080 (needs sudo for PID)
ss -tlnp | grep ':8080'             # simpler, same idea
lsof -i :8080                       # alternative: PID + command holding the port
fuser 8080/tcp                      # just the PID(s) bound to the port
```

When a service fails to start with **"Address already in use" (`EADDRINUSE`)**, there are two distinct cases:

1. **Another live process holds the port** — `ss -tlnp | grep :8080` names the PID; stop that process (or pick a different port). Common in dev when an old instance didn't exit.
2. **The port is in `TIME_WAIT`** from a *recently closed* socket (the previous instance of *your own* server). Here the listener is gone but the 4-tuple is reserved for ~60s. ss -tan state time-wait '( sport = :8080 )'   # confirm it's TIME_WAIT, not a live owner

The reasoning to show: distinguish "someone *else* is listening" (kill/relocate) from "my own socket is in TIME_WAIT" (SO_REUSEADDR) — they look identical in the error message but have opposite fixes.

#### Q95. [Coding] Write a Bash script that retries a flaky command with exponential backoff and jitter, giving up after N attempts.

```bash
#!/usr/bin/env bash
set -euo pipefail

retry() {
    local max="$1"; shift          # remaining args are the command
    local attempt=1 delay=1
    until "$@"; do
        if (( attempt >= max )); then
            echo "command failed after $attempt attempts: $*" >&2
            return 1
        fi
        local jitter=$(( RANDOM % (delay + 1) ))   # 0..delay seconds of jitter
        echo "attempt $attempt failed; retrying in $((delay + jitter))s" >&2
        sleep $(( delay + jitter ))
        delay=$(( delay * 2 ))      # exponential: 1, 2, 4, 8, ...
        (( attempt++ ))
    done
    return 0
}

# usage: retry 5 curl -fsS https://flaky.example.com/health
retry "$@"
```

Interview-worthy points: `until "$@"` runs the command and loops while it *fails* (non-zero), so it works with *any* command passed as arguments without `eval`; `delay=$(( delay * 2 ))` is the exponential schedule; and the **jitter** (`RANDOM % (delay+1)`) spreads retries so a fleet of clients doesn't synchronize into a thundering herd against a recovering service. The `(( attempt >= max ))` guard ensures a bounded, non-zero exit so callers/CI can react. This is the shell version of the resilience pattern you'd otherwise get from a library like Resilience4j.

#### Q96. [Practical] `df -h` says the root filesystem is 100% full, but `du -sh /` reports far less than the disk size. What's happening and how do you fix it?

This is the signature **deleted-but-still-open file** trap. A process (often a logger) has a large file open; someone `rm`'d the file to "free space," but because the process still holds the descriptor, the kernel keeps the data blocks allocated — `du` can't see it (no directory entry / name), yet `df` still counts the space as used. It's only reclaimed when the process closes the fd or exits.

```bash
# Find unlinked-but-open files and which process holds them
lsof +L1                        # +L1 = files with link count < 1 (i.e. deleted)
lsof / | grep -i deleted        # alternative phrasing
ls -l /proc/<pid>/fd | grep deleted   # confirm via /proc
```

Fix, safest first:

1. **Truncate via the descriptor** if the process is one you can signal to reopen, or simply **restart the holding process** — this releases the fd and the space returns instantly.
2. You can even *recover* the data before restarting: `cp /proc/<pid>/fd/<N> /tmp/recovered.log` reads the still-open content of the "deleted" file.

The second possibility worth ruling out: **inode exhaustion** (`df -i` shows 100% IUse with bytes free) when millions of tiny files fill the inode table — fixed by deleting the small files (often a runaway tmp/cache directory), not by adding disk. The meta-lesson: `du`/`df` disagreement almost always means *deleted-but-open*; `df -i` disagreement with `df -h` means *inodes*.

#### Q97. [Coding] Write an `awk` one-liner that sums a numeric column but only for rows where another column matches a condition (e.g. total bytes for 200-status requests).

#### Q98. [Practical] A deploy script does `cd $RELEASE_DIR && rm -rf *` and one day it wiped the wrong directory. What went wrong and how do you make such scripts safe?

The catastrophe is **`cd` silently failing**. If `$RELEASE_DIR` is *unset* or the directory doesn't exist, `cd $RELEASE_DIR` (unquoted, no error handling) fails but the script *keeps going*, so `rm -rf *` runs in whatever the current directory happens to be — possibly `$HOME` or `/`. Unquoted `$RELEASE_DIR` with spaces compounds it.

Hardening, layer by layer:

```bash
#!/usr/bin/env bash
set -euo pipefail                       # -u: unset $RELEASE_DIR is now a hard error
                                        # -e: a failed cd aborts the script

: "${RELEASE_DIR:?RELEASE_DIR must be set}"   # explicit, clear failure
[[ -d "$RELEASE_DIR" ]] || { echo "no such dir: $RELEASE_DIR" >&2; exit 1; }

cd "$RELEASE_DIR" || exit 1             # belt-and-suspenders: abort if cd fails
rm -rf -- "${RELEASE_DIR:?}"/*          # quoted, -- ends options, :? re-checks non-empty
```

The defenses, in order of importance: **`set -u`** turns an unset variable into an immediate error instead of an empty expansion; **`set -e`** plus an explicit `|| exit` means a failed `cd` can never fall through to the `rm`; **`${RELEASE_DIR:?}`** aborts if the variable is empty *at the point of the rm*; **`--`** stops `rm` from interpreting a path that starts with `-`; and quoting survives spaces. The cultural fix is to never `rm -rf` a glob in a variable directory without these guards, and ideally to `mv` to a timestamped trash dir instead of `rm` so mistakes are recoverable.

#### Q99. [Coding] Write a script that processes a CSV (handling a header row), filters rows by a column value, and outputs a selected subset of columns.

```bash
#!/usr/bin/env bash
```

#### Q100. [Practical] How do you compare two large files or directory trees to find what differs, and what tools fit which situation?

```bash
# Two files, line-by-line
diff -u old.conf new.conf            # unified diff (the patch/git format)
diff <(sort a.txt) <(sort b.txt)     # compare regardless of line order
comm -3 <(sort a.txt) <(sort b.txt)  # lines unique to each (3-column set logic)

# Two directory trees
diff -rq dirA dirB                   # recursive, quiet: just WHICH files differ
rsync -rvnc --delete dirA/ dirB/     # dry-run (-n) checksum (-c) compare → what rsync WOULD change

# Verify integrity by content, not name
find dirA -type f -exec sha256sum {} + | sort > a.sums
find dirB -type f -exec sha256sum {} + | sort > b.sums
diff a.sums b.sums                   # differences in actual content
```

Choosing the right tool: `diff -u` for *text* you'll review or turn into a patch; `comm` when you have two *sorted lists* and want set operations (only-in-A, only-in-B, common); `diff -rq` for a fast "which files changed" across trees; **`rsync -nc`** for large trees because it compares by checksum and shows exactly what a sync *would* transfer without doing it; and a **`sha256sum` manifest** when you need to prove two trees are byte-identical regardless of timestamps/paths (e.g. validating a backup or a build artifact). For binary files, `cmp` reports the first differing byte; `diff` alone just says "binary files differ."

#### Q101. [Coding] Write a function that prints a human-readable byte count (e.g. 1536 → "1.5K", 1073741824 → "1.0G").

```bash
human() {
    local bytes="$1" unit
    local units=(B K M G T P)
    local i=0
    # awk does the floating-point division the shell can't
    while (( bytes >= 1024 && i < ${#units[@]} - 1 )); do
        bytes=$(awk -v b="$bytes" 'BEGIN { printf "%.0f", b }')  # keep integer for compare
        # recompute with one decimal for display only at the end
        bytes_disp=$(awk -v b="$1" -v p="$i" 'BEGIN { printf "%.1f", b / (1024 ** (p+1)) }')
        bytes=$(( bytes / 1024 ))
        (( i++ ))
    done
    if (( i == 0 )); then printf '%dB\n' "$1"; else printf '%s%s\n' "$bytes_disp" "${units[i]}"; fi
}

human 1536          # 1.5K
human 1073741824    # 1.0G
```

The honest senior answer, though, is **don't hand-roll this** — the tools already do it correctly, including the awkward rounding and binary-vs-decimal (KiB vs KB) distinction:

```bash
numfmt --to=iec 1536            # → 1.5K   (GNU coreutils, IEC/1024 units)
numfmt --to=si 1500            # → 1.5K   (SI/1000 units)
ls -lh ; du -h ; df -h          # all take care of it for their own output
```

What this question really tests is judgment: showing you *can* write the loop (integer math in Bash, floating-point delegated to `awk` since Bash has no floats) but *recognizing* that `numfmt --to=iec` is the right production answer and that the KiB-vs-KB ambiguity is a real correctness concern, not a nitpick.

#### Q102. [Practical] An on-call alert says "high CPU." You SSH in. Give the exact sequence of commands and the decision tree to find the culprit in under two minutes.

```bash
uptime                          # 1. load over 1/5/15m — is it rising? compare to nproc
top                             # 2. press P (sort CPU); note %us vs %sy vs %wa; which PID?
#    or one-shot for scripting:
ps -eo pid,ppid,%cpu,%mem,comm --sort=-%cpu | head
nproc                           # 3. cores, to interpret the load number
pidstat -u 1 3                  # 4. per-process CPU over 3 samples (confirm it's sustained)
```

Decision tree once you see `top`:

```
high %us (user)   → a process is CPU-bound in userspace
   └─ which PID? → if it's the JVM: kill -3 <pid> (thread dump) or jstack,
                    look for a hot loop / busy thread; profile with async-profiler
high %sy (system) → kernel time: syscall storm, context switches, fork bomb
   └─ pidstat -w (context switches), strace -c -p <pid> for syscall profile
high %wa (iowait) → NOT cpu-bound: it's disk/IO (see the I/O runbook), iostat -x
%si/%hi high      → soft/hard IRQ pressure (network packet storm?) → check 'mpstat -P ALL'
one core pegged, rest idle → single-threaded hotspot → mpstat -P ALL confirms
```

The crisp method: `uptime`→`top`(P)→identify PID→classify `%us`/`%sy`/`%wa`. For a Java service the highest-leverage move is `kill -3 <pid>` (or `jstack <pid>`) to capture a **thread dump** and find the thread burning CPU — often a tight retry loop, a regex catastrophe, or a runaway GC. The two-minute discipline is *classify before you act*: `%wa` high means you're chasing the disk, not the CPU, and adding cores would do nothing.

#### Q103. [Practical] A service intermittently fails with "Too many open files." Walk through diagnosing and permanently fixing it.

`EMFILE`/"Too many open files" means the process hit its **`RLIMIT_NOFILE`** (open file-descriptor ceiling) — and "files" includes **sockets**, so it's frequently a leaked-connection problem, not literal files.

```bash
# 1. What limit is the RUNNING process actually under? (not your shell's ulimit!)
cat /proc/<pid>/limits | grep -i 'open files'
# 2. How many fds is it currently using, and trending?
ls /proc/<pid>/fd | wc -l
lsof -p <pid> | wc -l
# 3. WHAT are they? sockets piling up points to a leak; files to a different bug
lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn   # group by fd type
ls -l /proc/<pid>/fd | grep -c 'socket:'                       # socket count
```

Then split the fix into *capacity* vs *leak*:

- **Raise the ceiling** if the workload legitimately needs more (a busy proxy/DB). For a systemd service this is **`LimitNOFILE=65536`** in the unit's `[Service]` section — *not* `/etc/security/limits.conf`, which PAM applies to login sessions and systemd ignores. Verify with `/proc/<pid>/limits` after `daemon-reload` + restart.
- **Fix the leak** if the count grows unbounded under steady traffic — that's an application bug (HTTP clients/DB connections/streams not being closed). Watch `lsof -p <pid> | grep -c CLOSE_WAIT` or socket count climbing; a forever-growing `CLOSE_WAIT` set is the smoking gun of unclosed sockets, and *no* ulimit increase will save you — you'll just hit the higher limit later.

The senior framing: raising `LimitNOFILE` buys time and is correct for genuine scale, but if the fd count grows without bound the real fix is in the code. Diagnose *which* it is by watching the trend, not by guessing.

#### Q104. [Coding] Write a script that monitors a process by name and restarts it if it dies, with a backoff cap and logging — explaining why you'd normally let systemd do this.

```bash
#!/usr/bin/env bash
set -euo pipefail

cmd=( /opt/app/bin/server --config /opt/app/conf.yml )
max_delay=60
delay=1

log() { printf '%s %s\n' "$(date '+%F %T')" "$*"; }

while true; do
    log "starting: ${cmd[*]}"
    if "${cmd[@]}"; then
        log "process exited cleanly (0); not restarting"
        break
    fi
    rc=$?
    log "process died with code $rc; restarting in ${delay}s"
    sleep "$delay"
    delay=$(( delay * 2 > max_delay ? max_delay : delay * 2 ))   # capped backoff
done
```

This works, but the answer interviewers want is **"you almost never write this — systemd does it better."** A unit with `Restart=on-failure`, `RestartSec=5`, and `StartLimitIntervalSec`/`StartLimitBurst` gives you exactly this (supervised restart, capped retry, journald logging, restart *only* on failure not clean exit) plus crash-loop detection, dependency ordering, resource limits, and survives reboot:

```ini
[Service]
ExecStart=/opt/app/bin/server --config /opt/app/conf.yml
Restart=on-failure
RestartSec=5
StartLimitIntervalSec=300
StartLimitBurst=5          # >5 failures in 5min → give up, alert (no infinite crash loop)
```

The hand-rolled loop has real flaws to acknowledge: it has no crash-loop *ceiling* (it'll restart forever, masking a broken deploy), it dies if *it* is killed (it's not PID 1, nothing supervises the supervisor), and it doesn't distinguish "config is broken, stop trying" from "transient blip." Knowing when *not* to script — to push the concern down to the init system — is the mark of operational maturity.

#### Q105. [Practical] You suspect a process is leaking memory slowly over days. How do you confirm the trend and characterize it without guessing?

The key is **trend, not snapshot** — a single `ps` doesn't prove a leak. Sample RSS over time and correlate.

```bash
# Lightweight longitudinal sampling (run via cron or a loop; log to a file)
while true; do
    printf '%s %s\n' "$(date +%s)" \
        "$(awk '/VmRSS/{print $2}' /proc/<pid>/status)"      # RSS in kB
    sleep 60
done >> /var/log/rss-trend.log
# Then eyeball or plot the slope:
awk 'NR==1{first=$2} END{printf "delta=%d kB over %d samples\n", $2-first, NR}' /var/log/rss-trend.log
```

Characterize *where* the growth is, because the fix differs:

```bash
cat /proc/<pid>/status | grep -E 'VmRSS|VmSwap|VmData'   # resident vs swapped
cat /proc/<pid>/smaps_rollup                              # Rss/Pss/Private breakdown
pmap -x <pid> | sort -k2 -rn | head                      # which mappings are biggest
# For the JVM specifically:
jcmd <pid> GC.heap_info                                  # is it the HEAP growing?
jcmd <pid> VM.native_memory summary                      # off-heap (needs -XX:NativeMemoryTracking)
jmap -histo:live <pid> | head                            # what objects dominate the live set
```

The decisive diagnostic logic: if **heap** grows unbounded → a Java object leak (find it with a heap dump + MAT/`jmap -histo`); if **RSS grows but heap is flat** → *off-heap* (direct `ByteBuffer`s, metaspace, thread stacks from a thread leak, native libs, glibc arena fragmentation) — exactly the case that gets a container OOM-killed while the heap "looks fine." Confirming the leak is *sampling RSS over time and showing a monotone slope*; characterizing it is *splitting heap vs off-heap*. Snapshots lead to false conclusions; trends and the heap/off-heap split are what make the diagnosis defensible.

#### Q106. [Coding] Write an `awk`/Bash pipeline that, given an access log, reports request rate per minute so you can spot a traffic spike.

```bash
# Combined log timestamp looks like: [30/Jun/2026:14:23:51 +0000]
# Bucket by minute (strip seconds) and count
awk '{
    # $4 is "[30/Jun/2026:14:23:51" — cut to the minute
    ts = substr($4, 2)                 # drop leading [
    sub(/:[0-9][0-9] /, " ", ts)       # remove :SS, leaving ...:HH:MM
    minute = substr(ts, 1, 17)         # DD/Mon/YYYY:HH:MM
    count[minute]++
}
END { for (m in count) print m, count[m] }' access.log | sort | tail -20
```

A quick visual sparkline of the rate, if you have it, with `gnuplot` absent:

```bash
awk '{print substr($4,2,17)}' access.log | sort | uniq -c \
  | awk '{bar=""; for(i=0;i<$1/100;i++) bar=bar"#"; printf "%s %5d %s\n",$2,$1,bar}'
```

The technique: extract the timestamp field, **truncate to minute granularity** (drop the seconds), and count per bucket — the canonical "rate over time" shape. `sort | tail` shows the most recent minutes; sorting the counts (`sort -k2 -rn`) instead surfaces the *peak* minute. This is how you confirm "we got hammered at 14:23" from raw logs in seconds, before reaching for Grafana. For sub-minute resolution keep the seconds; for hour buckets truncate further. #### Q107. [Practical] How do you safely test a risky iptables/firewall change on a remote box without locking yourself out?

The nightmare is applying a rule that drops your own SSH session — now you can't connect to fix it. Several layered safeguards:

```bash
# 1. Schedule an automatic rollback BEFORE you make the change.
#    If you get locked out, the box reverts on its own in 5 minutes.
iptables-save > /root/fw.backup
echo 'iptables-restore < /root/fw.backup' | at now + 5 minutes   # auto-undo

# 2. Apply your change, then TEST from a SECOND ssh session (keep the first open!)
iptables -A INPUT ...            # your risky rule
#    open a new terminal: ssh user@box   — does it still work?

# 3. If good, cancel the rollback and persist:
atrm <job>                       # cancel the scheduled restore
iptables-save > /etc/iptables/rules.v4   # make it permanent
```

The discipline to articulate: **never make a connectivity-affecting change without a dead-man's switch.** The `at`-scheduled `iptables-restore` is the classic one — if your rule locks you out, you simply wait and the box restores itself; if it's fine, you `atrm` the job. Always keep your *existing* SSH session open and verify with a *new* one, because the existing connection may be grandfathered by an ESTABLISHED-allow rule while *new* connections are blocked. `firewalld` has this built in via `--timeout=`; nftables changes can be wrapped the same way. The principle generalizes: any change that could sever your control plane needs an automatic, time-boxed revert.

#### Q108. [Coding] Write a script that validates a config file's syntax (e.g. JSON/YAML) and exits non-zero with a clear message, suitable for a pre-deploy gate.

```bash
#!/usr/bin/env bash
set -euo pipefail

validate() {
    local f="$1"
    [[ -f "$f" ]] || { echo "MISSING: $f" >&2; return 2; }
    case "$f" in
        *.json)
            if ! jq empty "$f" 2>/tmp/err; then
                echo "INVALID JSON: $f" >&2; sed 's/^/  /' /tmp/err >&2; return 1
            fi ;;
        *.yml|*.yaml)
            # yq (or python) parses YAML; failure → non-zero
            if ! yq eval '.' "$f" >/dev/null 2>/tmp/err; then
                echo "INVALID YAML: $f" >&2; sed 's/^/  /' /tmp/err >&2; return 1
            fi ;;
        *) echo "UNKNOWN type: $f (skipping)" >&2; return 0 ;;
    esac
    echo "OK: $f"
}

rc=0
for f in "$@"; do validate "$f" || rc=1; done
exit "$rc"
```

Why this shape fits a CI/pre-deploy gate: it **exits non-zero on any invalid file** (so the pipeline stops before a bad config ships), prints the *underlying parser error* indented for readability, distinguishes "missing" (exit 2) from "malformed" (exit 1), and processes *all* files before failing (so one run shows you every broken file, not just the first). The tools do the real validation — `jq empty` parses JSON and fails loudly on syntax errors; `yq eval '.'` (or `python -c 'import yaml,sys; yaml.safe_load(open(sys.argv[1]))'` if `yq` isn't installed) does the same for YAML. For app-specific configs, prefer the app's own checker: `nginx -t`, `sshd -t`, `visudo -c`, `httpd -t`, `named-checkconf` — they validate *semantics*, not just syntax, which is strictly better.

#### Q109. [Practical] A production incident: latency spiked, then recovered, and you have only the logs and metrics after the fact. Reconstruct the timeline from the shell.

Post-hoc forensics is about *correlating independent evidence streams* around the incident window. Pin the window, then pull every source for that interval.

```bash
WINDOW='--since "2026-06-30 14:20" --until "2026-06-30 14:35"'

# 1. The app's own logs in the window, error-level and worse
journalctl -u myapp $WINDOW -p warning
# 2. Did the kernel do anything? (OOM kill, disk error, network reset)
journalctl -k $WINDOW | grep -iE 'oom|killed|error|reset|throttl'
# 3. System-wide events — restarts, other services, cron jobs that fired
journalctl $WINDOW | grep -iE 'started|stopped|failed|segfault'
# 4. Historical resource metrics (if sysstat/sar is enabled — it usually is)
sar -u -s 14:20:00 -e 14:35:00     # CPU
sar -r -s 14:20:00 -e 14:35:00     # memory
sar -d -s 14:20:00 -e 14:35:00     # disk
sar -n DEV -s 14:20:00 -e 14:35:00 # network throughput
# 5. Correlate request rate from access logs in the window
awk '$4 ~ /14:2[0-9]|14:3[0-5]/ {print substr($4,2,17)}' access.log | sort | uniq -c
```

The method that impresses: **establish a precise time window, then overlay every independent source on it** — app journal, kernel ring buffer (`journalctl -k`), historical `sar` metrics (the underrated hero: `sysstat` records CPU/mem/disk/net every 10 min by default, so you can look *backward* even though `top` only shows *now*), and request-rate from access logs. You're looking for what *changed first* at the leading edge of the spike: a deploy/restart (`Started`), an OOM (`journalctl -k`), a GC pause, a disk going to 100% `%util` in `sar -d`, or a traffic surge in the access log. The discipline is resisting the urge to grab the first plausible cause — line up the timeline and find the *earliest* anomaly, because that's usually the trigger and everything after is a symptom.

#### Q110. [Coding] Write a robust, idempotent deploy script skeleton: atomic release swap via symlink, health check, and automatic rollback on failure.

```bash
#!/usr/bin/env bash
set -euo pipefail

APP_ROOT=/opt/app
RELEASES="$APP_ROOT/releases"
CURRENT="$APP_ROOT/current"               # symlink → the active release
artifact="${1:?usage: $0 <artifact.tar.gz>}"
stamp="$(date +%Y%m%d-%H%M%S)"
new="$RELEASES/$stamp"

log() { printf '%s %s\n' "$(date '+%F %T')" "$*"; }

# capture the previous target so we can roll back
prev="$(readlink -f "$CURRENT" 2>/dev/null || true)"

rollback() {
    log "ROLLBACK to ${prev:-<none>}"
    [[ -n "$prev" ]] && ln -sfn "$prev" "$CURRENT" && systemctl restart myapp
    exit 1
}
trap rollback ERR                         # any failure below triggers rollback

log "unpacking $artifact → $new"
mkdir -p "$new"
tar -xzf "$artifact" -C "$new"

log "atomic symlink swap"
ln -sfn "$new" "$CURRENT"                  # ln -sfn is the ATOMIC pointer flip
systemctl restart myapp

log "health check"
for i in {1..10}; do
    if curl -fsS --max-time 3 http://127.0.0.1:8080/health >/dev/null; then
        log "healthy; deploy $stamp live"
        # prune old releases, keep last 5
        ls -1dt "$RELEASES"/*/ | tail -n +6 | xargs -r rm -rf
        trap - ERR                         # success: disarm rollback
        exit 0
    fi
    sleep 2
done
log "health check FAILED"
false                                      # trips the ERR trap → rollback
```

The load-bearing techniques: **`ln -sfn` is the atomic swap** — replacing a symlink is a single rename at the kernel level, so there's never a moment where `current` points at a half-deployed tree (unlike copying files into place). The **`trap rollback ERR`** disarmed on success (`trap - ERR`) means *any* failure between the swap and a passing health check automatically reverts the symlink to the previous release and restarts — bounded, automatic recovery. **Idempotence** comes from timestamped, immutable release directories (re-running doesn't clobber a live release) and `ln -sfn` being safe to repeat. The retry loop on the health check tolerates slow JVM warmup, and pruning keeps disk bounded while *retaining* recent releases so rollback targets still exist. This is the shape of Capistrano/symlink-based deploys distilled to its essentials.

#### Q111. [Practical] Explain how you'd find which process is generating unexpected outbound network traffic on a production host, end to end.

Unexpected egress (data exfiltration, a misbehaving client, a crypto-miner) requires tying *traffic* back to a *process*, which the obvious tools don't do directly.

```bash
# 1. Confirm there IS abnormal egress and roughly how much / where
ss -tnp                              # all TCP conns with PID/program (state, peer)
ss -tnp state established '( dport != :443 )'   # non-HTTPS established conns
iftop -i eth0                        # live per-connection bandwidth (interactive)
nethogs eth0                         # bandwidth grouped BY PROCESS — the key tool
# 2. Tie a suspicious remote endpoint to a PID
ss -tnp dst 203.0.113.50             # which process is talking to that IP
lsof -i @203.0.113.50                # same, via lsof
# 3. What IS the process and is it legit?
ls -l /proc/<pid>/exe                # the actual binary path (catches masqueraders)
cat /proc/<pid>/cmdline | tr '\0' ' ' # full command line
cat /proc/<pid>/environ | tr '\0' '\n' # injected env (LD_PRELOAD?)
# 4. Capture the actual traffic if you need proof
tcpdump -i eth0 -nn host 203.0.113.50 -w /tmp/egress.pcap -c 1000
```

End-to-end reasoning: **`nethogs`** is the fastest path because it attributes bandwidth *per process* directly (most tools show per-connection or per-interface, leaving you to map back to a PID). Once you have a suspect connection, **`ss -tnp dst <ip>`** or `lsof -i @<ip>` names the PID, and `/proc/<pid>/exe` + `/proc/<pid>/cmdline` reveal whether it's a legitimate service or something masquerading (a miner often names itself `kworker`-like; `readlink /proc/<pid>/exe` exposes the real binary in `/tmp` or `/dev/shm`). For evidence or deep analysis, a filtered `tcpdump -w` capture pulled into Wireshark shows exactly what's being sent. The security-incident discipline: identify → attribute to a process → verify the binary's legitimacy → preserve evidence (pcap, `/proc` snapshot) *before* killing it, so you can do root-cause/forensics rather than just stopping the symptom.

#### Q112. [Coding] Write a `trap`-based Bash pattern that guarantees a lock and a temp dir are cleaned up no matter how the script exits, and explain the failure modes it covers.

```bash
#!/usr/bin/env bash
set -euo pipefail

LOCK=/var/lock/myjob.lock
exec 9>"$LOCK"
flock -n 9 || { echo "already running" >&2; exit 1; }

workdir="$(mktemp -d)"

cleanup() {
    local rc=$?
    rm -rf -- "$workdir"          # remove scratch
    # fd 9 (and thus the flock) is released automatically on process exit,
    # but remove the lock FILE only if you created it and nobody else holds it
    flock -u 9 || true
    exit "$rc"                    # preserve the original exit code
}
trap cleanup EXIT                # runs on ANY exit path
trap 'exit 130' INT             # Ctrl-C → exit 130 → still fires EXIT trap
trap 'exit 143' TERM            # SIGTERM → exit 143 → still fires EXIT trap

# ... real work using "$workdir" ...
echo "working in $workdir (pid $$)"
```

The failure modes this covers and why a single `trap ... EXIT` is the linchpin:

- **Normal completion** — `EXIT` fires, temp dir removed, lock released by fd close.
- **Error under `set -e`** — a failing command aborts the script, but `EXIT` *still* runs, so no leaked scratch dir.
- **Ctrl-C (`SIGINT`) / `SIGTERM`** — the separate `INT`/`TERM` traps call `exit`, which *itself* triggers the `EXIT` trap (the crucial trick: signal traps that call `exit` funnel into the one cleanup path, so you write the cleanup logic *once*). Capturing `$?` first preserves the real exit code.
- **`flock` on the open file description** — the lock auto-releases when the process dies *even on `kill -9`* (which no trap can catch), so the single-instance guarantee survives a hard kill that bypasses every trap. That's why `flock` beats a PID-file lock: a `kill -9`'d PID file is left stale, but a `flock` is gone the instant the process is.

The one case nothing catches is **`SIGKILL`** — uncatchable by design — which is exactly why the *durable* resources (the lock) are tied to process lifetime (fd/`flock`) rather than to trap-based cleanup. The pattern: traps for the resources you must actively remove (temp dirs), kernel-lifetime mechanisms for the ones that must survive an unkillable death.

#### Q113. [Practical] You're handed an unfamiliar, undocumented production box and told "figure out what this server does" before a migration. What's your systematic recon?

Treat it like reverse-engineering: enumerate what *runs*, what it *listens on*, what it *talks to*, and what it *stores* — from the outside in.

```bash
# WHAT IT IS
hostnamectl ; cat /etc/os-release ; uname -a      # identity, distro, kernel
uptime ; last -n 20                                # how long up, who logs in

# WHAT RUNS (services & their purpose)
systemctl list-units --type=service --state=running
systemctl list-unit-files --state=enabled          # what starts at boot
ps auxf                                            # process TREE — see the hierarchy
crontab -l ; ls -la /etc/cron.* /etc/cron.d        # scheduled jobs (hidden work!)

# WHAT IT LISTENS ON (its role on the network)
ss -tlnp                                            # listening ports → identify the service
ss -tnp state established                           # who it's CONNECTED to (upstreams/DBs)

# WHAT IT TALKS TO (dependencies)
cat /etc/hosts /etc/resolv.conf                     # static mappings, resolvers
grep -rIl --include='*.{conf,yml,yaml,properties,env}' -e 'jdbc' -e 'host' /etc /opt 2>/dev/null
                                                    # config files pointing at DBs/upstreams

# WHAT IT STORES / WHERE THE DATA IS
df -hT ; mount ; cat /etc/fstab                     # filesystems, NFS/iSCSI mounts
du -h --max-depth=1 /var /opt /srv /data 2>/dev/null | sort -rh | head

# RECENT ACTIVITY (what's actually being used)
journalctl --since '7 days ago' -p warning | tail -50
find /opt /srv /data -type f -mtime -7 2>/dev/null | head  # recently touched files
```

The systematic frame to articulate: **identify (OS/host) → inventory running & enabled services → map listening ports to roles → trace established connections and config to find dependencies (databases, upstreams, message brokers) → locate the data (mounts, big directories, `fstab` for network storage) → check recent activity to separate live from dormant.** The migration-critical findings are the *dependencies you can't see from the process list* — `ss -tnp state established` reveals the databases and APIs it calls; `/etc/fstab` and `mount` reveal NFS/iSCSI storage that must move too; `crontab`/`/etc/cron.d` reveal batch jobs that would silently break; and `ss -tlnp` mapped to clients tells you *who depends on this box*. The judgment shown is breadth-first enumeration and an explicit hunt for *invisible* coupling (mounts, cron, established connections), because the thing that breaks a migration is always the dependency nobody documented.

## ✅ Key Takeaways

- **Composability is the philosophy.** Small tools joined by pipes (`grep | sort | uniq -c | sort -rn`) solve most text/log problems; learn the building blocks (`grep`, `sed`, `awk`, `cut`, `sort`, `uniq`, `tr`, `find`, `xargs`) and how `stdin/stdout/stderr` flow between them.
- **Permissions are octal + special bits.** Master `rwx`→`421`, `chmod`/`chown`/`umask`, and the setuid/setgid/sticky trio — and never reach for `chmod -R 777`.
- **Signals and graceful shutdown matter.** `SIGTERM` first (catchable, clean), `SIGKILL` only as a last resort (uncatchable, lossy); know that `SIGKILL`/`SIGSTOP` can't be trapped.
- **Write defensive scripts.** Start with `set -euo pipefail`, quote `"$variables"`, parse with `getopts`, check exit codes, and use `trap` for cleanup.
- **Troubleshooting is layered and tool-driven.** For load/CPU/mem/disk, go from symptom to cause with `top`/`vmstat`/`iostat`/`free`/`df`/`du`, and confirm reachability layer by layer with `ss`, `curl`, `nc`, `dig`, and `tcpdump`.
- **systemd + journalctl are the modern operational surface** — `systemctl start/enable`, `journalctl -u -f`, and timers over cron where logging and dependencies matter.

## ⚠️ Common Pitfalls

- **`uniq` without a preceding `sort`** — it only collapses *adjacent* duplicates, silently missing the rest.
- **Redirection order**: `cmd 2>&1 > file` sends stderr to the terminal, not the file; the correct order is `cmd > file 2>&1`.
- **Unquoted variables and filenames with spaces** — always `"$var"`, and use `find -print0 | xargs -0` (or `-exec ... +`) for safe filename handling.
- **`usermod -G` replaces secondary groups** — use `usermod -aG` to *append*, or you'll lock people out of `sudo`/`docker`.
- **`df` says full but `du` finds nothing** — a deleted-but-open file (`lsof | grep deleted`) or **inode exhaustion** (`df -i`); deleting an open log doesn't free space, *truncate* it instead.
- **`kill -9` as a reflex** — it skips shutdown hooks and risks corruption; try `SIGTERM` and wait first.
- **Cron's minimal environment** — no profile, sparse `PATH`; use absolute paths, set env vars explicitly, and redirect output or it gets mailed/lost.
- **JVM RSS exceeding `-Xmx`** — off-heap memory (metaspace, thread stacks, direct buffers, JIT) is real; "container OOM with healthy heap" means look *off*-heap and at cgroup limits.
- **`set -e` false confidence** — it's suppressed inside `if`/`&&`/`||` conditions and some substitutions; don't assume every failure aborts the script.

## 📚 Further Reading

- *The Linux Command Line* by William Shotts — the canonical free introduction (linuxcommand.org).
- *The Linux Programming Interface* by Michael Kerrisk — the deep reference for syscalls, processes, signals, and the `/proc` model.
- *Systems Performance* by Brendan Gregg — the definitive guide to load/CPU/memory/disk methodology, USE method, and `perf`/eBPF tracing.
- `man` pages and `info coreutils` — authoritative, offline, always current to your installed version; plus `tldr <cmd>` for quick examples.
- *Bash Reference Manual* (GNU) and Greg's Wiki / BashFAQ (mywiki.wooledge.org) — accurate Bash semantics, pitfalls, and best practices.
- *How Linux Works* by Brian Ward — clear coverage of boot, systemd, the filesystem, and networking internals.
- ShellCheck (shellcheck.net) — static analysis that catches the quoting/redirection/`set -e` pitfalls above before they bite.
